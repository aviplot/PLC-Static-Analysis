# M0 — Build scaffold, CI, `plc-core`

Status: **approved 2026-10-18, implemented** (see §8 for decisions and deviations)

## 1. Build

- **Gradle wrapper**, latest stable 9.x (exact version pinned in the wrapper; system Gradle here is 4.4 and unusable).
- **Kotlin DSL** with an included build `build-logic/` holding convention plugins, so module build files stay ~5 lines:
  - `plca.java` — toolchain, `--release`, `-Xlint:all -Werror`, JUnit 5 + AssertJ, Spotless, Checkstyle.
  - `plca.antlr` — applies `antlr`, sets ANTLR 4 version, `-visitor -no-listener`, package from module name.
    (Only applied by `plc-grammar` in M1.)
  - `plca.cli` — `application` + picocli (for `plc-cli` in M3).
- **Version catalog** `gradle/libs.versions.toml` for every dependency and plugin version.
- **Configuration cache and build cache on** from day one (`gradle.properties`), so slow builds are caught early.
- **All modules from the CLAUDE.md layout are created now** as empty skeletons with their dependency edges declared.
  The graph is fixed early, and the build enforces design rule 3:

  ```
  plc-core ← plc-ast ← plc-semantic ← plc-rules ← plc-report ← plc-cli
                 ↑                                              ↑
  plc-grammar ← frontend-{st,scl,l5x,plcopen} ──────────────────┘
  ```

  The frontends depend on the ANTLR runtime via `implementation`, so it never reaches the compile classpath of
  `plc-ast`/`plc-semantic`/`plc-rules`. A rule that tries to touch a parse tree doesn't compile. This is the same
  isolation as keeping the ABAP parser's internal tree out of the check framework.
- No JPMS `module-info` yet. It adds friction with the ANTLR runtime (automatic module), Jazzer and test
  classpaths; it can be revisited for M8 or a jlink distribution.

## 2. Static checks

- **Spotless + palantir-java-format** (120 columns, lambda-friendly). It formats Java, Kotlin DSL (ktlint) and
  `.g4` (trailing whitespace and line endings only). CI runs `spotlessCheck`; `./gradlew spotlessApply` fixes it locally.
- **Checkstyle** limited to what a formatter can't express: naming, no star imports, no `System.out`/`printStackTrace`
  outside `plc-cli`, no `@author`, file-size and method-length caps. No formatting rules, so it never conflicts
  with Spotless.
- `./gradlew build` = compile + tests + Spotless + Checkstyle. This is the "keep build green" gate.

## 3. CI (GitHub Actions)

- `.github/workflows/build.yml` runs on push and PR:
  - `./gradlew build` on Ubuntu with Temurin 21 and 25 (matrix).
  - `gradle/actions/setup-gradle` for caching.
  - Test reports uploaded on failure.
- A separate small job runs the harvester unit tests (`python -m unittest`) so `tools/` stays healthy.
- Placeholders later milestones fill in: SLL-fallback corpus check (M1), Jazzer smoke run (M1), JMH is manual/nightly (M2).

## 4. `plc-core` contents

Design principle: **spans are cheap integers in the coordinate system of the text the lexer saw, resolved to
what the engineer sees only at report time.** ANTLR token offsets map 1:1 onto spans with no per-token
allocation or lookup during parsing.

| Type | Purpose |
|---|---|
| `Dialect` | `CODESYS, TWINCAT, SIEMENS, ROCKWELL, PLCOPEN`. |
| `SourceFile` | A physical file: id, path, decoded text (BOM/UTF-16/UTF-8 with Windows-1252 fallback), detected charset. Immutable. |
| `SourceText` | Text a parser consumes. It is either the whole `SourceFile` or a **fragment** extracted from it (TwinCAT CDATA, L5X `<Text>`/`<Line>`, PLCopen `<ST>`), with a `SourceMap` back to the file. Holds a lazily built `LineIndex`. |
| `Span` | `record Span(int textId, int start, int end)`: half-open offsets in **UTF-16 code units** into a `SourceText`. UTF-16 matches `String` indices, ANTLR's `CharStream` for BMP text, LSP's default `PositionEncoding` and SARIF's default `columnKind: utf16CodeUnits`, so no conversion is needed at either end. |
| `LineIndex` | `int[]` of line starts; offset ↔ (line, column) by binary search. Handles `\n`, `\r\n` and bare `\r`. |
| `SourceMap` | Sorted segments `(fragmentStart, fileStart, length)`. Verbatim CDATA is one segment. Entity-escaped text (`&lt;` → `<`) gets one segment per unescaped run, so a position inside an expanded entity maps to the entity's start. Built by the XML frontends while they read StAX character events. |
| `SourceRegistry` | Thread-safe `textId → SourceText`. `resolve(Span) → Location(path, startLine, startCol, endLine, endCol)` in physical-file coordinates. |
| `Diagnostic` | `record Diagnostic(String code, Severity severity, String message, Span span, List<Related> related)`. These are frontend/semantic problems (`PLC-SYN-…`, `PLC-XML-…`). Rule findings in M3 reuse the same shape plus a rule id. |
| `Severity` | `ERROR, WARNING, INFO, HINT`. Maps to SARIF `error/warning/note/none` and to the LSP severities. |
| `DiagnosticSink` | Interface the frontends report into instead of throwing (design rule 2). Implementations are a per-file collector (no locking on the hot path, merged afterwards) and a counting/limiting decorator that caps the flood from one broken file. |

Tests (JUnit 5 + AssertJ), all on hand-written inputs:
- `LineIndex` with LF/CRLF/CR/mixed endings, a missing final newline, an empty file, a BOM, and surrogate pairs.
- `SourceMap`: a CDATA fragment inside a TwinCAT file, an entity-escaped PLCopen body, and a multi-line `<Text>`
  with CDATA. Each asserts the final file:line:col, written down by hand from the fixture.
- Charset detection for UTF-8 with and without BOM, UTF-16LE/BE and Windows-1252 (umlauts in German comments are common).

`plc-core` also gets **`java-test-fixtures`** with a small golden-file helper (`assertMatchesGolden(actual, path)`,
updated with `-Pgolden.update`). M1 needs it for parse-tree/AST snapshots, and test fixtures share it without
another module.

## 6. Decisions I need from you
1. **Java baseline.** CLAUDE.md says "Java 21+ (current LTS)", but Java 25 is the current LTS.
   *Recommendation: compile with `--release 21`, CI on 21 + 25.* This keeps the widest install base. Moving to 25
   later costs one line, and nothing we need is 25-only.
2. **CI host.** The repo has no remote yet. Is it GitHub (Actions as above), or GitLab/other?
3. **Formatter.** palantir-java-format (my pick: 120 columns, better lambdas and builder chains) or google-java-format (100 columns).
4. **`corpus/MANIFEST.csv`** is 20 MB and will grow with each harvest. Options: keep committing it as is, commit
   `MANIFEST.csv.gz`, or Git LFS. *Recommendation: gzip.* Diffs are useless at this size anyway, and `STATS.md`/`SOURCES.md`
   are the files people actually read.

## 8. Decisions and as-built notes
- Decisions: `--release 21`, tests also on JDK 25; palantir-java-format; **no hosted CI for now** —
  `scripts/ci.sh` runs the same steps locally (build on 21, tests on 25, harvester tests);
  `corpus/MANIFEST.csv` stays local (git-ignored).
- Pinned versions (each released ≥ 2 weeks before adoption): Gradle 9.8.0, Spotless 8.10.3,
  palantir-java-format 2.100.0, Checkstyle 14.3.0, JUnit 6.1.3, AssertJ 3.27.7, ANTLR 4.13.2, picocli 4.7.7.
- Base package **`dev.plca`** (placeholder — cheap to rename now, expensive after M1).
- `LineIndex` lives on `SourceFile`, not `SourceText`: resolution always maps a fragment offset to the file first,
  so fragments never need their own line index.
- Added `XmlText`: decodes an element's character content straight from the raw file text (CDATA, entities,
  character references, newline normalisation, comments/PIs) and builds the `SourceMap` at the same time. StAX is
  then only needed to find content boundaries; its own text and offsets are unreliable for mapping. Exact StAX
  offset handling is an M1 task (`// TODO(verify-format)` where the parser's offsets are used).
- `plc-grammar` applies plain `plca.java` until M1 adds the first grammar and switches it to `plca.antlr`
  (which already strips the ANTLR tool from `api`).
