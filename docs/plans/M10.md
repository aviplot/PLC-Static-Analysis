# M10 — Incremental model, load progress, SFC drawings, report drawings, packaging

Status: **draft, awaiting approval**.

## Goal
The follow-ups of M8 and M9 that the owner picked (2026-10-20):
1. **Incremental semantic model**: a keystroke rebuilds only the units it affects, not the whole model group.
2. **Load progress** in the web workbench and VS Code while a project is parsed and analysed.
3. **SFC drawings** next to the ladder and LD/FBD drawings.
4. **Ladder / LD / FBD / SFC drawings in the HTML report**.
5. **Finding counts per routine** in the web workbench's diagram list.
6. **Edited files download in their original encoding** (and BOM).
7. **No Java installation needed**: a bundled runtime for the VS Code extension, `plca` and `plca web`.

## 1. Incremental semantic model
### Where the time goes today
`Workspace.snapshot()` reuses unchanged *groups*, but rebuilds a changed group from scratch: declare → types → bind
→ effects → tasks → instances. Measured in M8: 125 / 266 ms (p50 / p95) on the 240k-line generated project, 649 /
798 ms on TC-Robot-Control-System, where every keystroke in any small file rebinds one unrelated 7.6 MB generated FB.
Half the rebuild is filling the identity side tables (`symbols`, `types`, `effects`, …).

### Why symbols cannot simply be kept
Symbols point at AST nodes (`PouSymbol.declaration()`, `VariableSymbol.declaration()`, initializers), and those nodes
hold spans. An edit replaces the whole unit's AST, so even a body-only edit makes the changed unit's symbols stale:
a declaration below the edit would point to the wrong line for go-to-definition, hover and findings. Decoupling
symbols from nodes (Roslyn-style declaration references) would touch about 105 call sites in rules, navigation and the
builder. That is decision 1 (b); I recommend (a) below.

### Design (decision 1 (a)): rebuild a dependency closure of units
- **Dependencies recorded during a build**, per unit: *declaration* edges (a variable, base, interface, alias or
  constant of U resolves to a symbol owned by unit D) and *body* edges (a body or initializer of U binds a symbol of D).
  Kept on the model as two small `unit → set of units` maps.
- **On an edit of unit C**, the new model is built from the previous one:
  1. *Re-declare set* R: C, plus every unit with a declaration edge to a unit in R (transitively), because their
     symbols hold `Type.Instance(pou)`, `Type.Struct(symbol)`, … of replaced symbols. In practice this follows
     instance nesting upwards (an FB, the FBs that hold it, the program that holds those): small.
  2. *Re-bind set* B: R plus every unit with a body edge to a unit in R (callers, users of its variables). Their
     symbols stay; only their bodies are bound again.
  3. **Global scope** copied (a few thousand entries) with R's entries replaced. **Side tables** cloned
     (`IdentityHashMap.clone()` is an array copy), entries of B's old nodes removed, B bound again. Call graph rebuilt
     from the call sites (cheap); task model and instance graph rebuilt only when R touched a declaration they use.
- **Full rebuild instead** when the incremental path cannot be sure, decided before any work:
  - the set of global names changed (a POU, type, GVL or global added, removed or renamed), because previously
    unresolved or duplicate names elsewhere may now bind differently;
  - C is a configuration / task unit, a Rockwell controller export (one unit is the whole controller anyway), or a
    Siemens unit with data blocks other units use by absolute address;
  - R ∪ B exceeds a third of the group's units, where a full build is no slower.
- **Correctness check**: `ModelPrinter` output of the incremental model must equal that of a full build.
  - `IncrementalModelTest`: on every fixture project, each unit edited (body-only edit, declaration edit, rename,
    delete, add).
  - `WorkspaceFuzzTest` gets a model-equality oracle.
  - A `modelCheck` devtools task replays random edits on corpus projects.
  - A hidden `-Dplca.model.verify=true` makes the language server compare both builds and log differences.

**Targets** (`EditCycleBenchmark`, single thread):

| Project | Fast tier p95 target |
|---|---|
| Generated 240k-line project | < 60 ms (today 266 ms) |
| TC-Robot-Control-System, typical file | < 150 ms (today 798 ms) |
| 24k-line project | no slower than today (11 ms) |

**Limit, stated up front**: an edit *inside* the 7.6 MB file still re-parses and rebinds that file (the unit is the
smallest step). Parsing below unit level (re-parsing just the changed POU of a file) is not in M10.

## 2. Load progress
- `ProjectLoader.load` and `Workspace.loadAll` get a progress callback reporting files parsed / total and bytes, then
  phases: "building model", "running rules".
- **Language server**: standard LSP work-done progress (`window/workDoneProgress/create` + `$/progress` begin / report
  / end), only when the client announces `window.workDoneProgress`. VS Code shows it in the status bar with no
  extension code.
- **Web workbench**: the own LSP client handles the same messages and shows a progress bar with the phase, file count
  and percentage. It replaces the spinner in the findings panel and the diagram view.
- **Decision 2**: also answer `plca/diagram` for a file from a parse of that file alone while the project still loads
  — **recommended**. Progress alone tells the user why the 43 MB L5X takes 3.8 s; this makes its first ladder appear
  in about 1 s (the M9 target). Findings on the rungs appear when the analysis is done.

## 3. SFC drawings
| Source | Positions in the export | Analysed today | M10 |
|---|---|---|---|
| PLCopen XML | yes (`position`, `connectionPointIn`, sizes) | yes (`Sfc` IR, lowered to statements) | draw |
| L5X `Type="SFC"` routines | yes (`X`/`Y` on `Step`, `Transition`, `Branch`, …) | no: skipped with a diagnostic | read and draw, decision 3 |
| TwinCAT `<SFC>` | serialized `XmlArchive` object dump, undocumented | no | decision 3 |

- **IR**: `Sfc` today keeps only the resolved semantics (divergences and jumps are folded into transitions). A drawing
  needs the chart as drawn, so a new `Sfc.Layout` (elements: step, transition, selection / simultaneous divergence
  and convergence, jump, macro step, action block, each with box and connection points) sits next to the semantics.
  The PLCopen reader fills both from the same XML elements.
- **Renderer**: `SfcSvg` in `plc-report`, in the style of `NetworkSvg`: steps as boxes (double border for initial),
  transitions as bars with their condition text, single lines for selection branches and double lines for simultaneous
  ones, action blocks to the right of their step with qualifier and duration, and jumps as arrows with the target
  name. Findings are highlighted on the step or transition that carries their span. If the export has no positions,
  a layered layout from the graph is used, as for FBD.
- **L5X SFC**: the element names and attributes in the corpus (31 files) look regular, but I have not checked them
  against Rockwell's *Logix 5000 Controllers Import/Export* manual (1756-RM084). I'll write `docs/grammar/l5x.md` §SFC
  from the corpus with `TODO(verify-format)` on every element I could not confirm, and you check it against the manual
  if you have it.
- **Tests**: golden SVGs, `renderCheck` extended to SFC on all corpus files that have SFC (222 PLCopen, 31 L5X).

## 4. Drawings in the HTML report
- For each finding whose span lies in a rung, network or SFC element, the report embeds that drawing (just that
  rung or network, not the whole routine) below the finding's source excerpt, with the element highlighted.
  The SVGs come from `Diagrams` and are inlined, so the report stays one self-contained file.
- Size guard: identical drawings are embedded once and referenced (`<use>` / a shared `<template>`). After 2,000
  drawings (or about 20 MB) further findings show text only, and the report says so.
- `plca analyze --format html --report-diagrams findings|none` (default `findings`; `none` gives today's report).
  The web workbench's HTML download uses the same default.
- **Tests**: golden HTML with drawings for the `plant` and `rockwell_line` fixtures; size check on the largest
  corpus L5X.

## 5. Finding counts per routine (web workbench)
- `plca/diagrams` already lists the routines and networks of a file. Each entry gets its text range, and the client
  counts the file's current findings inside it, so counts follow live edits without a new request.
- The list shows a count badge coloured by the worst severity, and gets an "only with findings" toggle and a "sort by
  findings" option. Selecting an entry scrolls to its first finding.
- **Tests**: unit test for the counting; e2e: the `rockwell_line` routine with the double coil shows its count.

## 6. Downloads in the original encoding
`TextDecoder` already records charset and BOM (UTF-8 with or without BOM, UTF-16 LE/BE, Windows-1252). The browser
currently re-encodes everything as UTF-8 without BOM, which breaks Windows-1252 umlauts and UTF-16 exports when they
are imported back into the IDE.
- `POST /api/projects/{id}/export` with the edited texts. The server encodes each file with its original charset and
  BOM and returns the zip. The client stops zipping by itself.
- Characters the original charset cannot hold (an `€` typed into a Latin-1-only file is fine in 1252, a `→` is not):
  - That file is written as UTF-8 with BOM.
  - If it is XML, the `encoding="…"` in its declaration is changed to match.
  - The UI lists those files before the download ("saved as UTF-8: these characters do not exist in Windows-1252").
- Line endings are kept: Monaco keeps the file's EOL, which is checked in the e2e test.
- **Tests**: round trip per charset (unchanged file → identical bytes), the unmappable-character case, and e2e
  download of an edited Windows-1252 file.

## 7. Running without a Java installation
**Short answer: yes.** `jlink` builds a trimmed Java runtime containing only the modules plca uses, and we ship it
inside the extension and the `plca` zip. Users never install Java.
- **Modules**: from `jdeps --print-module-deps` on all jars, probably `java.base`, `java.xml`, `java.logging`,
  `java.net.http`, `jdk.unsupported`, a few more. Expected size about 40–50 MB unpacked, 20–25 MB zipped, per platform.
- **One build per platform**, because the runtime is native code. `jlink` can link for another OS from Linux, given
  that platform's JDK `jmods`, so one CI job can produce all of them.
- **VS Code**: platform-specific VSIX files (`vsce package --target win32-x64 linux-x64 darwin-arm64 …`). The
  Marketplace (or the user) installs the matching one, and the extension starts the bundled runtime. A user's own
  `plca.javaHome` setting still overrides it.
- **CLI and `plca web`**: `plca-<version>-<os>-<arch>.zip` with `bin/plca(.bat)` using the bundled runtime. A
  Docker image for `plca web` is a cheap extra.
- **Alternatives considered**:
  - GraalVM `native-image` (one binary, fast start): needs reflection configuration for Jackson, Gson/LSP4J, picocli
    and Jetty, and Community Edition is noticeably slower on long analyses, which risks the 1M-lines-in-10-s target.
    Not recommended now.
  - `jpackage` installers (`.msi`, `.pkg`, `.deb`): must be built on each OS. Useful later if you want installers
    rather than zips.
- **Decision 4**: which platforms. Signing is decision 5.

## Decisions needed
1. **Incremental model.** (a) Unit-level rebuild of a dependency closure, with a full-rebuild fallback and an
   equality oracle — **recommended**. (b) Symbols decoupled from AST nodes, so body-only edits never touch other
   units: faster in the worst case, but a refactor of about 105 call sites and every rule's access to declarations.
2. **Early diagrams while loading.** (a) Yes, from a parse of that file alone — **recommended**. (b) Progress only.
3. **SFC sources.**
   (a) PLCopen and L5X — **recommended**. L5X SFC routines are also lowered to the same `Sfc` semantics, so the
   rules run on them (today they are skipped). The reader is written from corpus files and marked
   `TODO(verify-format)`.
   (b) PLCopen only.
   (c) Also TwinCAT SFC, reverse-engineered from the 192 corpus files. Not recommended: the format is an undocumented
   object serialization, and CLAUDE.md says not to guess vendor formats.
4. **Platforms for the bundled runtime.** Recommended: `win32-x64` (most controls engineers), `linux-x64`,
   `darwin-arm64`. Optional: `linux-arm64` (edge devices), `darwin-x64` (older Macs).
5. **Code signing.** Unsigned zips and VSIX files work, but Windows SmartScreen warns about an unsigned `java.exe`
   from the internet, and macOS Gatekeeper blocks un-notarized binaries until the user allows them. Signing needs a
   certificate (Windows) and an Apple Developer account (macOS), which only you can obtain. Recommended: build
   unsigned now with the signing step as a hook in the CI job, and add the certificates when you have them.
