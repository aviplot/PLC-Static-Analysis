# M12 — Corpus-driven parser fixes

Status: **approved 2026-10-25**, decisions 1–3 as recommended.

## Goal
The P0 harvest was re-run on 2026-10-25 (8,656 candidate repos, 108,016 unique files, 46.3 M lines).
`corpusCheck` parses all of it in about 40 s and now also writes every error diagnostic
(`parse-errors.tsv`) and every distinct normalised message (`error-messages.tsv`). M12 turns that log into a
**repeatable fix loop**, then runs the loop over the largest failure clusters. No new languages, no rule changes.

## The fix loop (repeatable, one cluster per pass)
1. **Run** `./gradlew :plc-devtools:corpusCheck` (≈ 40 s for the whole corpus).
2. **Triage** with a new `corpusTriage` task (below): first error per file, noise excluded, clustered by
   `format + code + normalised message`, ranked by **repos**, then files. Repos rank first because the baseline is
   repo-weighted and one large repo should not set the order.
3. **Pick** the top cluster; open 3–5 files from different repos and decide what it is:
   - **(a) missing grammar feature** (valid ST/SCL the grammar does not accept) → fix;
   - **(b) dialect difference** (valid in CODESYS but not SCL, or the reverse) → fix in the dialect grammar or with a
     small predicate (Grammar rule 3);
   - **(c) wrong frontend behaviour** (XML unwrapping, file classification, spans) → fix in the frontend;
   - **(d) invalid input** (real syntax errors, truncated files) → no fix; if recovery is poor (one error
     wiping out the rest of the POU), improve the error strategy so recovery is better;
   - **(e) noise** → add it to the noise list.
4. **Fix** in the order "How to work in this repo" requires: note in `docs/grammar/<dialect>.md` citing the spec
   section (or `TODO(verify-format)` when vendor behaviour is unclear) → a **hand-written** minimal test and golden
   file (corpus code becomes a fixture only from `fixture-ok` repos, with attribution) → grammar → AST builder.
5. **Verify**: `./gradlew build` green; corpus run with no format dropping, the SLL-fallback check still passing,
   parse time within ±10 %; then `-PupdateBaseline`.
6. **Commit** one cluster per commit, with before/after numbers in the message.

## Tooling (first step, before any grammar change)
- **Re-baseline.** `corpus-baseline.properties` describes the old, smaller corpus; six rates are now "below
  baseline" only because the corpus changed. Regenerate it on the new corpus first, so later passes measure
  against the real starting point.
- **Noise list** `modules/plc-devtools/corpus-noise.txt`: repo or path patterns excluded from the rates and the
  triage (committed; it lists only repo names, no code). Excluded files are still parsed, so no crash can hide
  there.
- **`corpusTriage`** task (or `CorpusCheck --triage`): writes `triage.md` / `triage.tsv` (cluster, files, repos,
  5 example locations from different repos) into the git-ignored reports directory.
- Optional `-Ponly-failing`: re-parse only the files in the last `failures.tsv`, for a fast edit–test loop on one
  cluster.

## Order
Tooling and re-baseline → TwinCAT (highest code quality, 128 repos, already 99 %) → Siemens SCL and classic SCL →
`.st` → PLCopen → L5X. Inside a family, by repo count. Every cluster is checked on the files before any work starts;
the column above is a guess from the messages only.

**Done** when every family's repo-weighted rate reaches its target (decision 2) or the remaining clusters are all
(d)/(e), each listed in an "As built" section with its counts.

## Decisions
1. **Generated code**: exclude it from rates and triage via the noise list but keep parsing it (recommended; it
   still tests error recovery), or remove those repos from the corpus.
2. **Targets** (repo-weighted, without noise): TwinCAT ≥ 99.5 %, SCL ≥ 97 %, scl-classic ≥ 92 %, `.st` ≥ 92 %,
   PLCopen ≥ 95 %, L5X file ≥ 97 % (recommended), or fixed time-boxes per family instead.
3. **Classic STEP 7 SCL** (437 files, 71 repos): in scope (recommended; it is the same grammar with unquoted
   names), or deferred.
