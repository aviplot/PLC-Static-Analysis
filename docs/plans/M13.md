# M13 — Logic rules (condition reasoning and branch structure)

Status: **approved, built** (decisions in §6, as built in §7).

## Goal
A new rule family **`logic`**: findings that prove a branch can never run, a condition is always true or false, or a
branch structure says something other than what was meant. Inspired by the ABAP logic-rules catalog (an earlier
analyzer of the owner's); ported where the idea holds for IEC 61131-3 code, dropped where it is ABAP- or SQL-specific
or already covered by an existing PLCA rule. The design is ours, written for `plc-ast` and `plc-semantic`. No code is
copied.

## 1. What carries over, and what does not

| ABAP catalog | PLC | Why |
|---|---|---|
| 1–6, 8–11, 14 contradictions, tautologies, unreachable branches, duplicate conditions/labels, boundary gaps | **ported** (L001–L011) | Same IF / ELSIF / CASE / WHILE structure; integer ranges and enums make them *more* decidable in PLC code |
| 31 literal longer than the field | **generalised** (L012) | `STRING(n)` vs a longer literal, plus comparisons outside the type's range (`USINT < 0`, `BYTE > 255`, enum vs a value it cannot hold) |
| 12, 13, 16, 17, 19–23 structure (identical branches, self-assignment, ELSE→ELSIF, merge IFs, ELSE after RETURN, empty branch, boolean through IF, same statement in every branch) | **ported** (L013–L021) | Plain ST structure; `IF c THEN b := TRUE; ELSE b := FALSE;` is very common in PLC code |
| 29 loop that ends in its first pass | **ported** (L022) | FOR/WHILE/REPEAT whose body ends in an unconditional EXIT/RETURN |
| 32 value overwritten before use | **ported, narrowed** (L023) | Only VAR_TEMP and FUNCTION/METHOD locals. Static VARs keep their value across cycles, so an earlier write may be read next cycle or by another task |
| 43 `NOT x IS INITIAL` | **adapted** (L024, off by default) | `NOT (a = b)` → `a <> b` |
| 42 boolean vs a non-boolean text | **adapted** (L025, off by default) | `IF bFlag = TRUE` → `IF bFlag` (style) |
| 7 unreachable code, 15 CASE without OTHERS, 18 deep nesting, 28 loop condition never changes | **not added** | Already PLCA-Q009, Q002, Q013, Q012 |
| 25, 26 sy-subrc, 41 sy-tabix, 30/44 CHECK | **not added** | ABAP-only system fields / statements |
| 101–112 SQL / joins | **not added** | No SQL in PLC code |

## 2. Rules

IDs `PLCA-L001`…, category `logic`. Severities use our scale: a proof of dead or wrong code = `warning`, style = `info`.
PLCopen ids only where verified against the guidelines document (else `-`, as for Q002).

| ID | Title | Sev. | Default | Ladder/FBD |
|---|---|---|---|---|
| L001 | Contradictory nested condition (never true given the enclosing conditions) | warning | on | — |
| L002 | Unreachable ELSIF (false whenever the earlier branches are false) | warning | on | — |
| L003 | Unreachable ELSE of an IF chain (earlier branches cover every case). **Never for CASE ELSE**: Q002 asks for it as a defensive branch | warning | on | — |
| L004 | Self-contradictory condition (`a > 10 AND a < 5`, `XIC(A) XIO(A)` in series) | warning | on | **yes** |
| L005 | Duplicate condition in an IF/ELSIF chain | warning | on | — |
| L006 | Duplicate or overlapping CASE label (`1..10` and `5`) | warning | on | — |
| L007 | Tautological condition (`a > 5 OR a <= 5`; parallel legs `XIC(A)` / `XIO(A)`) | warning | on | **yes** |
| L008 | Condition always true where it is (implied by the enclosing conditions) | warning | on | — |
| L009 | ELSIF that should be ELSE | info | on | — |
| L010 | Redundant part of a condition (`a > 10 AND a > 5`; the same contact twice in series) | info | on | **yes** |
| L011 | IF chain without ELSE that misses a boundary (`a < 0` / `a > 0` misses 0) | warning | on | — |
| L012 | Comparison outside the operand's range (`usi < 0`, `by > 255`, `STRING(4)` = 6-char literal) | warning | on | **yes** |
| L013 | Identical branches (IF/ELSE alike, or two CASE branches with the same statements) | warning | on | — |
| L014 | Self-assignment (`x := x;`, `MOV(A, A)`) | warning | on | **yes** |
| L015 | ELSE that holds only an IF (use ELSIF) | info | on | — |
| L016 | Nested IF without ELSE inside IF without ELSE (merge with AND) | info | on | — |
| L017 | ELSE after a branch that always leaves (RETURN / EXIT / CONTINUE / JMP) | info | on | — |
| L018 | Empty THEN with an ELSE (negate the condition) | info | on | — |
| L019 | BOOL set through IF (`b := c;`) | info | on | — |
| L020 | Same statement first or last in every branch (hoist it) | info | on | — |
| L021 | Empty branch with no comment | info | on | — |
| L022 | Loop that ends in its first pass | warning | on | — |
| L023 | Temp/local value overwritten before it is read | info | on | — |
| L024 | NOT before a comparison | info | **off** | — |
| L025 | BOOL compared with TRUE/FALSE | info | **off** | — |

"Ladder/FBD = yes": the rule also runs on conditions lowered from rungs and networks (contacts in series = AND,
branches = OR), reporting the span of the contacts in the rung (design rule 5). The other rules skip lowered code, as
Q009 and Q013 already do: its IF structure and `$rc` power-flow variables are synthetic. Before relying on this, the
lowering is checked on the golden files: one contact = one atom, `$rc` variables inlined for the analysis.

## 3. Engine (`plc-rules`, package `dev.plca.rules.logic`)

| Class | Role |
|---|---|
| `Cond` / `Atom` / `Operand` | Normalised condition: AND/OR/NOT tree over comparison atoms, with NOT pushed into the atoms and operands in a fixed order (`5 < a` → `a > 5`). BOOL designators are propositions. Anything else (calls, arithmetic other than `a - b`, pointer dereference, indexes that are not constant) is an opaque atom keyed by its normalised text. A call atom never equals another. |
| `Normalizer` | `Expression` → `Cond`, using `SemanticModel.type` and `SemanticModel.constant`. Operand domains come from the types: integer ranges per `ElementaryKind` (SINT…ULINT, BYTE…LWORD), subranges, enum value sets, REAL dense, `STRING(n)` length, TIME as an integer. Caps on atoms per condition. |
| `IntervalReasoner` | Satisfiability and implication by DNF (capped) plus per-operand interval/point-set intersection. **Unsatisfiable is a proof; "satisfiable" is reported only when exact**, else UNKNOWN. `coverageGaps` for L011. |
| `Facts` | Immutable conjunction carried by one top-down walk per POU body: IF/ELSIF/ELSE (with the negations of the earlier branches), CASE labels, WHILE at the start of the body, the join after a block (branches that always leave do not count). |
| `LogicWalk` | The walk that L001/L002/L003/L008/L009/L011 share. It runs once per POU and caches the result on the `PouContext`, so each rule reads it rather than walking again. |

**Invalidation (PLC-specific).** A fact on an operand is dropped when:
- any statement writes it (`SemanticModel.effects(s).accesses()`);
- an FB, method or function call that may write it runs: VAR_IN_OUT / REFERENCE TO arguments, the FB instance's own
  outputs (`fbTimer.Q` after `fbTimer(...)`), and every global or `THIS^` member on a call to user code;
- it is reached through a pointer, a reference or an `AT %` overlay (volatile: dropped on any write);
- it is a global that PLCA-P004's task model shows is written by another task (preemption may change it between two
  reads);
- at the start of each loop pass, for everything the loop body writes.

**Quiet by design** (as in the ABAP version, adapted):
- conditions fixed by literals or named constants are Q009's (`includeNamedConstants` switch), never L001/L004/L007;
- `WHILE TRUE` with an EXIT is the endless-loop idiom (Q012 covers it);
- `x = x` on REAL is the NaN check (as in Q003), so it is not a tautology;
- CASE ELSE is never "unreachable" (L003), even when an enum CASE covers every value.

## 4. Configuration and tests
- Descriptors `PLCA-L0xx.md` (id, title, severity, dialects, rationale, compliant/noncompliant), parameters via
  `plca.yaml` (`maxAtoms`, `maxTerms` on the engine rules; `ignoreWithComment` for L021). Suppression comments
  work unchanged. `logic` becomes a selectable category.
- Fixtures `plc-rules/src/test/resources/PLCA-L0xx/` (ST, plus `rockwell/` and `plcopen/` for the ladder-enabled
  rules), each with positive, negative and "looks similar but is fine" cases (operand written in between, FB call in
  between, pointer alias, a global written by another task, REAL vs DINT bounds).
- Unit tests for `Normalizer` and `IntervalReasoner`.
- **Differential test** (seeded random conditions over 1–3 operands of integer/REAL/BOOL/enum type, with facts and
  chains) against an SMT oracle, to prove the reasoner never claims a wrong UNSAT. Needs JavaSMT + SMTInterpol in test
  scope only (§6.3).
- Jazzer: the existing `RulesFuzzTest` covers the new rules automatically.

## 5. Order
1. Engine + unit tests + differential harness (no disagreements before any rule ships).
2. L004, L007, L010, L012, L014 (single-condition rules, ladder included).
3. Walk + L001, L002, L003, L005, L006, L008, L009, L011.
4. Structure: L013, L015–L021.
5. L022, L023, L024, L025.
6. Corpus run (`corpusCheck` + analyze): findings per rule, 10 samples per rule reviewed locally (corpus code stays
   out of the repo), the share of conditions the engine leaves UNKNOWN and why, rule time against the M12
   baseline (target < 10 % extra). False positives fixed before "As built".

## 6. Decisions (were open points)
1. **IDs / category**: `PLCA-L001…L025`, category `logic`. OK?
2. **Severity / defaults**: proofs `warning`, style `info`; L024 and L025 off by default. Should the structure rules
   (L015–L021) also be opt-in, like Q014/Q015, since vendor style guides differ?
3. **SMT oracle**: add JavaSMT + SMTInterpol (LGPL, test scope only, not in the distribution). Fetching them needs
   network access once. Or skip the differential test and rely on hand-written reasoner tests?
4. **Ladder scope**: L004 / L007 / L010 / L012 / L014 on rungs and networks as listed. Any others?
5. **Ordering and change rules**: is it right to treat a global written by another task as volatile (§3)? It costs
   some findings in single-task projects that the export does not mark as such.

Answers: 1 yes. 2 yes: L015–L021 are opt-in too, with L024 and L025. 3 yes, test scope only. 4 yes. 5 yes, but
report the proof at `info` instead of dropping it, with a note naming the task (`… (assuming 'g' is not changed by
task Fast in between)`).

## 7. As built

- 25 rules in `dev.plca.rules.logic`. L001–L012 share one analysis per POU (`LogicAnalysis`, computed once, read by
  each `ConditionRule`). L013–L025 are separate rules. Opt-in: L015–L021, L024, L025.
- Suppression comments and `plca.yaml` accept `PLCA-L…` ids and the `logic` category. The JSON report schema
  allows `PLCA-L…` ids and the `logic` category.
- **Differential test** (`DifferentialTest`): random conditions over INT subranges, DINT, USINT, REAL, BOOL, STRING(3)
  and a constant, checked against SMTInterpol through JavaSMT. 10k conditions per build; 300k more across seeds 1–3
  found one soundness bug (a subrange domain applied to arithmetic, now a regression case).
- **Corpus** (75,068 files, 36.5 M lines, all rules on): no rule failures. Findings: L001 697, L002 106, L003 117,
  L004 267, L005 71, L006 24, L007 72, L008 542, L009 1,240, L010 1,222, L011 360, L012 1,215, L013 11,297,
  L014 3,570, L015 3,213, L016 3,207, L017 883, L018 58, L019 3,260, L020 1,209, L021 2,311, L022 89, L023 578,
  L024 15,197 (13,242 in PLCopen, mostly generated test XML), L025 8,027.
- **Performance**: the first corpus run spent 63% of rule time in the logic rules. Fixes: branch comparison on the AST
  (`Structural`) instead of printed text (L013 165 s → 5 s summed), the per-model task map built outside the global
  lock (`Races`), and conditions that are AND / OR / NOT over distinct BOOL names (most lowered ladder) skip the
  reasoner. Corpus wall time is 44 s with the logic rules and 35 s without (+27%, over the 10% target). Remaining cost
  is the expression pass over large Rockwell projects, which the corpus check runs on one thread per project.
  **Follow-up**: cache reasoner results per POU and profile the Rockwell expression pass.
