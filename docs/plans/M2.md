# M2 — Semantic model for ST, JMH benchmarks

Status: **approved 2026-10-18 ("ok, do m2")**.

## Goal
One semantic model (design rule 4) that rules in M3 query instead of walking raw syntax: symbols, resolved types,
name bindings, expression types, read/write sets, call graph, FB-instance graph and the task model. Built from
`plc-ast` only, for a whole project (many files), never failing on incomplete projects (libraries are usually not
part of an export).

## Architecture (module `plc-semantic`, package `dev.plca.semantic`)
Classic multi-pass analyzer, each pass reading the previous pass's tables:

| Pass | Output |
|---|---|
| 1. Declare | `GlobalScope`: POUs, user types, GVLs (and their variables), enum values, namespaces. Duplicates → `PLC-SEM-002`. |
| 2. Resolve types | `TypeRef` → `Type` for every variable, member, return type, type alias (with cycle detection). |
| 3. Bind bodies | For every name/member/call in every body: the `Symbol` it refers to and the expression's `Type` (side tables, keyed by identity). |
| 4. Derive | per-statement `Effects` (reads, writes, calls); `CallGraph`; `InstanceGraph`; `TaskModel`. |

- **Symbols**: sealed `Symbol` — `PouSymbol` (with kind, owner for members, `EXTENDS`/`IMPLEMENTS` resolved),
  `VariableSymbol` (section, qualifiers, type, initial value, pragmas, owner POU or GVL), `TypeSymbol`
  (struct/union/enum/alias/subrange), `EnumValueSymbol`, `GvlSymbol`, `LibrarySymbol` (unresolved external).
- **Types**: sealed `Type` — `Elementary` (IEC + CODESYS elementary types with category, bit size, signedness),
  `StringType(wide, length)`, `ArrayType`, `PointerType(kind)`, `StructType`, `UnionType`, `EnumType`,
  `InstanceType` (FB/class/program/interface), `AliasType`, `SubrangeType`, `Unknown(name)`.
- **Scoping (CODESYS rules)**: locals of the POU/member, then the owning FB (methods, actions, properties), then
  `EXTENDS` chain, then GVL variables (not for `{attribute 'qualified_only'}` lists, which need `GVL.x`), then
  global POUs/types, then enum values unless `{attribute 'strict'}`/`'qualified_only'`. `THIS^`/`SUPER^` bind to
  the FB. Library prefixes the project doesn't define (`Tc2_Standard.TON`) are looked up by their last part in the
  builtins, otherwise they become `LibrarySymbol`s — never an error.
- **Builtins**: a Java table of IEC standard function blocks (TON, TOF, TP, R_TRIG, F_TRIG, CTU, CTD, CTUD, SR, RS)
  with their inputs and outputs, standard functions with result-type rules (fixed, "like argument n", conversion
  `X_TO_Y`/`TO_Y`), and CODESYS operators (`ADR`, `SIZEOF`, `REF`, `__NEW`, `__QUERYINTERFACE`, …).
- **Expression types** cover what M3 rules need: literals (typed prefixes, smallest-fit integers as `ANY_INT`
  literal type), variables, member/index/deref, calls, binary/unary operators via IEC generic-type promotion.
  The implicit-conversion legality check itself is a rule (M3), not part of the model.
- **Constant evaluation**: integer/real/bool/time folding over literals and `VAR CONSTANT`s (for constant-false
  `IF`, division by constant zero and array bounds in M3).
- **Effects**: an `Access` is a root variable plus a selector path (`fb.Q`, `arr[*].x`) and READ/WRITE/READ_WRITE.
  FB calls write the instance's inputs and read its outputs (`Q => y` writes `y`), `VAR_IN_OUT` arguments are
  read+write, `REF=`/`ADR` mark the target as aliased (address taken). Compound statements report their own
  condition reads; `Effects.deep(stmt)` aggregates nested ones.
- **Call graph**: function, FB-instance, method, action, property-get/set edges with call-site spans;
  recursion and "called more than once per cycle" are queries on it (rules in M3/M7).
- **Instance graph**: static instance tree from task programs (or every PROGRAM if no task config) through FB
  instance variables, arrays of FBs included, depth-limited against recursive types.
- **Task model**: IEC `CONFIGURATION/RESOURCE/TASK/PROGRAM … WITH`; TwinCAT `.TcTTO` (`<Task Name>`, `<CycleTime>`
  in µs, `<Priority>`, `<PouCall><Name>`; format verified against two public repos). Read by a small StAX reader in
  `frontend-st`, delivered as AST `Declaration.Configuration`, so the semantic model sees one task representation.
  Without task configuration the model reports "unknown" rather than guessing.

## Project loading (`frontend-st`)
`ProjectLoader`: walks a directory, parses `.st` / `.TcPOU/.TcDUT/.TcGVL/.TcIO/.TcTTO` in parallel (one `StFrontend`
per thread), returns the units plus the shared `SourceRegistry` and diagnostics. TwinCAT: one PLC project per
`.plcproj` directory when present.

## JMH (`frontend-st/src/jmh`, own source set, `./gradlew :frontend-st:jmh`)
- `ParseBenchmark`: two-stage (SLL first) vs LL-only on generated representative ST (and on a corpus
  directory when `-Pjmh.corpus=<dir>` is given), lines/s.
- `SemanticBenchmark`: model build for a generated 200-POU project.
- No plugin: plain source set + `jmh-generator-annprocess` + `JavaExec` (the Gradle JMH plugin's last release
  predates Gradle 9).

## Corpus check extension
Per repository: load as a project, build the model, record crash-freedom, time, and **name-resolution rate**
(bound names / all names, unresolved library names counted separately). Baseline the rate like the parse rate.

## Tests
Hand-written multi-file projects in `plc-semantic/src/test/resources/` with golden dumps of symbols, types,
bindings, effects, call graph, instance graph and tasks; targeted tests for scoping rules (qualified_only, strict
enums, EXTENDS, SUPER^, actions/methods seeing FB vars), constant folding and type promotion. The semantic tests
build their ASTs through `frontend-st` (test dependency only; main code depends on `plc-ast` alone).

## Out of scope
Rules (M3); evaluating `{IF defined}` (both branches stay; duplicate-declaration diagnostics inside conditional
regions are suppressed); SCL/L5X/PLCopen symbols (M4–M6; the model is dialect-neutral so they plug in).

## As built (2026-10-18)
- `plc-semantic`: `SemanticBuilder` (4 passes), `SemanticModel` (symbols, types, parameters, constants, effects,
  owners, call graph, instance graph, tasks, resolution stats, unresolved names), `ModelPrinter` for goldens.
- `frontend-st`: `ProjectLoader` (parallel, path-ordered), `TwinCatTaskReader` (`.TcTTO` → `Configuration`), and an
  LL-only switch (`new StFrontend(false)`) used by the benchmark.
- New dev-only module **`plc-devtools`** (never shipped): `corpusCheck` and `parseDebug` moved here from
  `frontend-st` because the check now needs the semantic model; JMH benchmarks in its `jmh` source set.
- Harvester: `.TcTTO` added; 2,043 task files from 997 repos re-fetched.
- **Corpus** (per project: `.plcproj` directory or repository; 3,423 projects, 6.4M name occurrences):

  | group | resolved | library (unknown prefix/type) | unresolved | resolved+library, repo-weighted |
  |---|---|---|---|---|
  | TwinCAT | 83.5% | 12.3% | 4.2% | 95.9% |
  | `.st` | 81.2% | 11.9% | 6.9% | 86.8% |

  No project produced an internal error. Inspected unresolved names are library functions and constants used
  without a prefix (`MEMCPY`, `ADSLOGSTR`, TcUnit `AssertTrue`, `PI`), declarations in files the harvester does not
  collect (B&R `.var`), and genuine undeclared variables. Baselines in `plc-devtools/corpus-baseline.properties`.
- **JMH** (`./gradlew :plc-devtools:jmh`, generated 203-file / 18.6k-line project, one thread, laptop):

  | benchmark | ms/op | |
  |---|---|---|
  | parse, two-stage | 27.0 ± 2.2 | ≈ 690k lines/s per thread |
  | parse, LL only | 39.4 ± 9.3 | two-stage is ~31% faster |
  | semantic model build | 9.7 ± 0.2 | |

  The corpus check (all 17.9M lines, 8 threads, parse + per-project model) runs in ~37 s. Parsing alone is well
  inside the "1M lines < 10 s" target.
- Fuzzing: `SemanticFuzzTest` (parse + build + queries), ~570k executions, no failures.
- Decisions taken while building: a call `F(...)` inside function F binds to F (recursion), not to its result
  variable; CASE labels may use unqualified values of the selector's (even strict) enum; references and pointers
  dereference implicitly for member access (tolerant: TwinCAT accepts `pFb.x` in places); counters use `WORD`
  (CODESYS) not `INT` (IEC).
