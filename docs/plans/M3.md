# M3 — Rule engine, first 10 rules, JSON/SARIF output, CLI (first demoable build)

Status: **approved 2026-10-18 (rule selection "assume it's OK"; PLCopen IDs verified against the official document)**.

## Goal
`plca analyze <path> --format sarif` on a CODESYS/TwinCAT project prints findings that point at what the engineer
sees in the IDE. The run never fails on bad input. Ten rules are chosen to show the three kinds of checks: quality,
PLC-specific and security. Rules use only `plc-semantic` and `plc-ast` (design rule 3) and are written once for
every dialect (design rule 4).

## Architecture
The classic analyzer layout is a rule registry, a rule engine that walks the model once and fans out to rules, a
findings collector, and report writers.

| Module | Content |
|---|---|
| `plc-rules` (`dev.plca.rules`) | `Rule` SPI, `RuleDescriptor` (metadata), `RuleRegistry`, `RuleEngine`, `RuleConfig`, `Finding`, the 10 rules in `dev.plca.rules.<category>` |
| `plc-report` (`dev.plca.report`) | `ReportWriter` for `console`, `json`, `sarif` (Jackson); `AnalysisResult` (findings + diagnostics + run info) |
| `plc-cli` (`dev.plca.cli`) | picocli `Main` with `analyze` (and `rules`, which lists rules with their metadata) |

### Rule SPI
- Two kinds of rule, both behind one sealed `Rule` interface:
  - **`PouRule`**: `check(PouContext)` runs once per POU body (members included). The engine runs these in parallel
    over POUs on the fixed thread pool. Most rules are this kind.
  - **`ProjectRule`**: `check(ProjectContext)` runs once per model. For cross-POU facts: double coil (writes across
    POUs), recursion (call-graph cycles), unused variables (GVL variables read from anywhere).
- The contexts expose the `SemanticModel`, the POU's `PouSymbol`, the rule's parameters (typed, with defaults from
  the descriptor), and `report(span, message, related…)`. Rules don't build their own walkers. `PouContext` offers
  `statementsDeep()`, `expressionsDeep()` and the M2 `Effects`, so each rule is a filter over model facts. That is
  the "query, not traversal" style that kept the ABAP checks small.
- **Isolation**: an exception in one rule on one POU becomes diagnostic `PLC-INT-002` (rule id, POU, stack top). The
  rule and POU are skipped and the run goes on, the same policy as parser recovery.
- **Determinism**: findings are sorted by (path, offset, rule id) whatever the thread schedule, so golden tests and
  SARIF diffs stay stable.

### Rule metadata: one source per rule
`plc-rules/src/main/resources/dev/plca/rules/<RULE_ID>.md` holds front matter for `id`, `title`, `severity`,
`category`, `dialects`, `tags`, `parameters`, `plcopen` and `cwe`, followed by Markdown sections *Description*,
*Rationale*, *Noncompliant*, *Compliant*. It feeds SARIF `rules[]` (`shortDescription`, `fullDescription`,
`help.markdown`), `plca rules`, and later the HTML report (M7). A test checks that every registered rule has a
descriptor, every descriptor has a rule, and the examples in it produce, or do not produce, the rule's finding.

### Rule IDs
Our own stable IDs: `PLCA-<category letter><nnn>` (**Q** quality, **P** PLC-specific, **S** security), plus the
PLCopen *Coding Guidelines* v1.0 (official release, 2016-04-20,
<https://www.plcopen.org/downloads/>) rule in the `plcopen` field where one applies. IDs below were checked against
the PDF's rule sections ("Identifier: Rule …"), not secondary summaries. Note: the document's table of contents lists
the FOR-loop rule as **L22**, but its section 6.5.4 says **Rule L12**; we cite L12 and mention L22 in the help text.
The PLCopen document is copyrighted: descriptors cite rule ID and title only and never copy its text.

## The first 10 rules
These were chosen for demo value and because M2 already provides each fact they need.

| ID | PLCopen | Rule | Kind | Model facts used | Default severity |
|---|---|---|---|---|---|
| PLCA-Q001 | CP24 | Unused variable (declared, never read or written; inputs/outputs/GVL vars excluded or handled per section) | Project | `Effects`, symbols, `{attribute 'hide'}`-style exemptions | warning |
| PLCA-Q002 | — (L17 covers IF only) | CASE without ELSE (and not all enum values covered) | POU | AST + enum type of selector | warning |
| PLCA-Q003 | CP8 | Equality/inequality comparison on REAL/LREAL | POU | expression types | warning |
| PLCA-Q004 | — | Division or MOD by literal/constant zero | POU | constant evaluator | error |
| PLCA-Q005 | L12 | FOR loop variable assigned inside the body | POU | `Effects` writes of the loop variable | warning |
| PLCA-Q006 | CP17 | Write to a VAR_INPUT inside its own POU | POU | `Effects`, variable section | warning |
| PLCA-Q007 | CP13 | Recursion (direct or indirect) | Project | `CallGraph.cycles()` | error |
| PLCA-P001 | CP12 (physical outputs; we also check other variables) | Double coil: same output/variable unconditionally driven from more than one place | Project | writes per root variable + path; `related` points at every other write | warning |
| PLCA-P002 | N1 | Direct/absolute addressing in code (`%I`, `%Q`, `%M`) instead of a symbolic variable | POU | `DirectAddress` nodes (declaration `AT %…` is allowed) | info |
| PLCA-S001 | — | Hard-coded credential or IP address in a string literal | POU | literals + variable names (`password`, `pwd`, `token`, …) + IPv4/IPv6 patterns | warning |

**Double coil precision** decides whether the demo convinces controls engineers, so the rule is narrowed on
purpose. It flags a variable *assigned* (`:=`, or an FB output via `=>`) in more than one statement of the same scan
path. It does not flag `S=`/`R=` pairs, writes in mutually exclusive `IF`/`CASE` branches of the same statement,
initialisation in a first-scan block, or `VAR_TEMP`/locals of functions. Each excluded case gets a negative test.
The corpus run (below) measures the rest.

## Configuration (M3 scope)
- `--rules <ids|categories|all>` (default: all M3 rules), `--disable <ids>`, `--param PLCA-Q001.ignoreHidden=false`.
- `RuleConfig` is a plain record that the CLI builds today and `plca.yaml` will build in M7. No YAML parser in M3.
- No inline suppressions or baselines yet (M7). SARIF results carry `partialFingerprints` from the start, so
  baselines will work on M3 reports. The fingerprint is a hash of rule id + POU qualified name + normalised
  statement text, without line numbers.

## Reports
- **console** (default on a TTY): `path:line:col: severity PLCA-Q003 message`, the source line with a caret
  underline, related locations indented, and a summary per rule and severity.
- **json**: our own stable format with `schemaVersion: 1`, `tool`, `rules[]`, `findings[]` (resolved `Location` +
  related), `diagnostics[]` (parse/semantic problems), and `stats` (files, lines, POUs, time, resolution rate).
  Its JSON Schema goes in `docs/report-json.schema.json`.
- **sarif** 2.1.0:
  - `tool.driver.rules[]` from the descriptors.
  - Results carry `ruleId`, `ruleIndex`, `level`, `locations` (artifact URI relative to `%SRCROOT%`, the analysed
    root), `relatedLocations` and `partialFingerprints`.
  - Spans are resolved through `SourceRegistry`, so CDATA text in TwinCAT XML maps to file line and column (design
    rule 5). The column unit is UTF-16 (`columnKind: utf16CodeUnits`).
  - Parser and semantic diagnostics go to `invocations[0].toolExecutionNotifications`, which is the SARIF place for
    problems processing the input, so they don't mix with rule findings.
  - The output is validated against the official SARIF 2.1.0 JSON schema in tests. That needs a schema validator as
    a test-only dependency (networknt `json-schema-validator`) and the OASIS schema file in test resources.
- New dependencies: Jackson `jackson-databind` (CLAUDE.md stack), and the schema validator (test only).

## CLI
```
plca analyze <path> [--format console|json|sarif] [--output <file>] [--rules …] [--disable …] [--param k=v]
                    [--fail-on error|warning|info|never] [--threads n] [--base <dir>]
plca rules [--format console|json]
```
- `<path>` is a directory or a single file. Loading uses the M2 `ProjectLoader`. Only CODESYS/TwinCAT files are
  analysed for now; other dialects are listed as "skipped, not yet supported".
- Exit codes: `0` no finding at or above `--fail-on` (default `error`), `1` findings at or above it, `2` usage error
  or unreadable path. Bad *content* never gives a non-zero exit on its own.
- `./gradlew :plc-cli:installDist` builds `build/install/plca/bin/plca`. A smoke test runs the installed CLI on the
  `plant` test project.

## Tests
- Per rule, in `plc-rules/src/test/resources/<RULE_ID>/`:
  - `noncompliant.st` and `compliant.st`, plus extra cases where a rule needs more than one file. TwinCAT XML is
    used for at least one rule, to check CDATA span mapping.
  - Expected findings are **inline markers** in the source, the way the error-prone/Checkstyle test harnesses do
    it: `// PLCA-Q003` (or `(* PLCA-Q003 *)`) on the line where the finding must start. The harness checks that the
    findings and the markers match exactly, with no extra and no missing findings. A golden file of full messages
    and related locations (`expected.txt`, rewritten with `-Pgolden.update`) catches message drift.
- Engine tests: parallel and sequential runs give identical output; a rule that throws becomes `PLC-INT-002` and
  the run goes on; parameters parse and use their defaults.
- Report goldens: console/JSON/SARIF for the `plant` project, plus SARIF schema validation.
- Jazzer: the existing semantic fuzz target extended to run all rules. The invariant is no exception escapes and
  every finding span resolves.
- Descriptor test as above (examples in each `.md` are checked by the rule itself).

## Corpus check extension (`:plc-devtools:corpusCheck`)
- Run every rule on every corpus project. Report crash-freedom (`PLC-INT-002` count must be 0), time per rule,
  findings per rule per 1k lines, and **20 random findings per rule** written to `build/corpus/rule-samples/` for
  manual review.
- I review the samples and record an estimated false-positive rate per rule in "As built". Any rule above about
  20% FP gets fixed or narrowed before M3 is closed.
- Performance target: rules add **< 30%** to parse + model time on the corpus. A JMH benchmark `RuleBenchmark` on
  the generated 200-POU project tracks it.

## Order of work
1. Dependencies (Jackson, schema validator) and the SPI/engine/registry/descriptor loader, with engine tests.
2. Test harness (inline markers + goldens), then the rules one at a time, each with tests.
3. Reports (console, JSON, SARIF + schema validation), then the CLI and smoke test.
4. Fuzz extension, corpus check extension, FP review, JMH. Update `As built` and commit in small steps.
