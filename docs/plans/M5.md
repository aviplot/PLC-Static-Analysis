# M5 — L5X frontend: tags, UDTs, AOIs, rung grammar lowered to IR, ST routines

Status: **done 2026-10-19; approved 2026-10-19** (module I/O: option A; power-flow temporaries only where needed; FBD/SFC after M6, L5K out of scope). Grammar notes
will go in `docs/grammar/rockwell.md` (written first, after approval).

## Goal
Read Rockwell Studio 5000 `.L5X` exports with StAX. Turn the project's data types, tags, AOIs, programs, routines and
tasks into the **same** `plc-ast` as ST and SCL:
- ladder (RLL) rungs are parsed with their own small grammar and **lowered to ST-style statements** (design rule 4);
- ST routines are parsed with a Rockwell ST dialect on the shared core.

Build the semantic model for Rockwell projects and run the M3 rules on them, so double coil, unused tags and direct
I/O use work on ladder logic. Validate against the L5X files in the corpus.

## What the corpus says
2,052 `.L5X` files from 176 repos (169 contribute L5X); 2,039 are well-formed XML. The 13 that are not are mostly
deliberate test fixtures: truncated files, bad UTF-8, and **two XXE attack files** (`malicious-xxe.l5x`,
`xxe-big.l5x`). So the reader must turn off DTDs and external entities. The TwinCAT reader already does this.

| Root `TargetType` | Files | Routine `Type` | Routines | Feature | Files / count |
|---|---|---|---|---|---|
| Controller (full project) | 639 | RLL | 32,920 | rung text in CDATA | 1,534 files |
| AddOnInstructionDefinition | 491 | ST | 1,282 (75k lines) | AOIs (with local tags) | 753 files / 1,761 AOIs |
| DataType | 319 | FBD | 143 | Tasks: CONTINUOUS / PERIODIC / EVENT | 426 / 308 / 26 |
| Routine | 202 | SFC | 65 | Alias tags | 128 files / 7,774 tags |
| Program | 165 | Encrypted / `EncodedData` | 4 / 81 files | Safety programs / tags | 208 / 69 files |
| Module | 145 | | | Produced / consumed tags | 57 / 48 |
| Rung | 56 | | | UDT `BIT` members on a hidden host (`Target`, `BitNumber`) | common |

Rungs: **3.05M**, but `jholm90/logixMemoryMap` (82%) and `johnpuksta/l5x-lint` (14%) are generated. All metrics are
therefore **repo-weighted**, as in M4. Without those repos and one other generator there are 67.6k rungs:
- 26% use bit access `.N`;
- 13% index with a variable (`a[i]`);
- 7% use module I/O tags (`CP6RIO0:I.Data[5].2`);
- 6% have `?` placeholders (`TON(t,?,?)`);
- 3% have expression operands (`CPT(x,(a-b)/c*2.0)`);
- 1% use `\Program.Tag` scoping.

Branch nesting goes up to 6 or more (depth ≥ 2 in 1% of rungs). There are 693 distinct mnemonics. The top 16 (XIC, OTE,
XIO, MOV, EQU, TON, ADD, GRT, LES, OTU, OTL, ONS, NEQ, COP, CTU, JSR) make up > 99% of instruction uses; the
long tail is mostly AOIs (instruction names defined in the project). Software revisions run from v16 to v38, with
most at v32–v37.

ST routines are stored line by line (`<Line Number="n"><![CDATA[…]]></Line>`). They use `/* … */` and `//`
comments, and keywords appear as tag names (a tag called `DINT`).

## Key decisions

### 1. Reader: StAX over the decoded text (`frontend-l5x`)
- `L5xReader` uses the same Woodstox setup and offset technique as `TwinCatReader` (DTD and external entities off,
  depth limit). It builds a small **project skeleton**: controller, data types, AOIs, tags, programs, routines, tasks
  and modules. Each piece of embedded text (rung `<Text>`, ST `<Line>`, operand-free attributes) is recorded only as
  a file offset range. `XmlText`/`SourceMap` turn ranges into fragments with exact spans, as for TwinCAT CDATA.
  - An ST routine is one fragment built from its lines, joined with `\n` through `SourceMap.replacement` (the
    builder already supports this). A finding then reports the line the engineer sees in the routine editor.
- **Memory**: no DOM, no parse trees kept. The decoded `SourceFile` text is held, as for every frontend, because
  spans and line mapping need it. The largest corpus file is 43 MB (≈ 86 MB as a `String`). That is fine for
  now; a memory test on that file goes into the corpus check. A lazily-read `SourceFile` for files in the
  hundreds of MB is listed as a follow-up and is not built speculatively.
- Partial exports (`TargetType` Routine / Rung / AOI / DataType / Program) are read the same way: whatever is present
  becomes the unit. References to tags that aren't in the file become external symbols (as Siemens PLC tags do).
- `<Data Format="Decorated">` gives tag initial values (needed for read-before-assignment in M7). The `L5K`
  format string is skipped in M5.
- L5X element/attribute details that I can't confirm from the corpus are marked `TODO(verify-format)` in the
  notes and listed for you. One example: the operand order of AOI calls in rungs (backing tag, then InOut and visible
  required parameters).

### 2. Rung grammar: `RungLexer.g4` / `RungParser.g4` (grammar rule 6)
- `rung : element* ';' EOF`
- `element : instruction | branch`
- `branch : '[' leg (',' leg)* ']'` (empty legs allowed)
- `instruction : MNEMONIC '(' operand (',' operand)* ')'`
- `operand : tagPath | literal | '?' | expression-text`
- `tagPath` covers `\Prog.Tag`, `Program:Main.Tag`, module I/O `Rack1:2:I.Data[3].5`, member access, `[i,j]`
  indexes (expressions allowed) and `.N` bit access.
- **Expression operands** (CPT, CMP, FAL, FSC, and calculated indexes): the rung grammar only matches balanced
  operand text. The builder parses the operand span again with the **Rockwell ST `expression` entry rule**, using an
  offset source map, so there is one expression grammar for both ST and ladder.
- No keywords: mnemonics are identifiers followed by `(`, and whitespace between elements is allowed. The SLL /
  two-stage driver and the error strategy from the kit are reused. Recovery syncs to `,`, `]`, `)` and `;`.
- Rung text and its comment (`<Comment>`) are kept. Rung comments go on the comment channel equivalent, for
  suppressions later.

### 3. Rockwell ST: `RockwellStLexer` / `RockwellStParser` import the shared core
The same pattern as M1 and M4 (grammar rule 3):
- Entry rule `routineBody : statement* EOF`. Declarations come from XML, not text.
- `/* */` comments are added to the hidden channel. The core types and keywords become soft identifiers where the
  corpus shows them used as names.
- Module-tag and `\Program` designators are shared with the rung grammar's `tagPath` rules.
- Non-retentive assignment `[:=]`.
- Instruction calls such as `TONR(t)`, `JSR(...)` and `MOV(a,b)` are ordinary calls, resolved by the semantic model
  through the instruction table.
- `TODO(verify-format)` items (against the Logix 5000 Structured Text Programming Manual, 1756-PM007): the exact
  keyword set, `RETURN` vs `RET()`, `EOT`/`SFR`, and the CASE label forms.

The builder kit gives the `RockwellAstBuilder` the same shared glue as SCL. The M4 conformance test is extended to
check that core ST statements produce identical ASTs.

### 4. Lowering ladder to the shared IR (design rule 4)
A rung becomes ST-style statements by tracking **power flow** from left to right. The rung condition starts at
TRUE:
- an input instruction ANDs a term onto it (XIC `a` → `a`, XIO → `NOT a`, EQU → `a = b`, …);
- a branch evaluates each leg from the incoming condition and ORs the legs;
- an output instruction becomes a statement that uses the current condition.

| Rung | Lowered (printed form) |
|---|---|
| `XIC(A)[XIC(B),XIO(C)]OTE(D);` | `D := A AND (B OR NOT C);` |
| `XIC(S)OTL(M);` / `OTU` | `IF S THEN M := TRUE; END_IF` (`FALSE` for OTU) |
| `XIC(R)MOV(5,X)ADD(X,1,Y);` | `IF R THEN X := 5; Y := X + 1; END_IF` |
| `XIC(E)TON(T1,?,?);` | `TON(T1, EnableIn := E);` (instance call, writes T1.EN/TT/DN/ACC) |
| `XIC(G)JSR(Fill,0);` | `IF G THEN Fill(); END_IF` (call-graph edge to the routine) |
| `XIC(A)ONS(OS)OTE(B);` | `$rc1 := A AND ONS(OS); B := $rc1;` |

- **Every instruction is evaluated exactly once.** When a condition is used more than once after a side-effecting
  input instruction (ONS, OSR, an AOI used as an input), it goes into a synthetic power-flow variable (`$rc1`,
  `Identifier.Form.SYNTHETIC`). Rules never report synthetic variables. The printer shows them, so goldens catch
  lowering mistakes. Pure conditions are inlined. The shared records make this cheap.
- OTE writes **unconditionally** (`D := cond`), which is exactly what makes double coil a real bug in ladder.
  OTL/OTU are conditional set/reset, and the existing P001 already handles set/reset pairs.
- **Instruction table** (`plc-semantic`, data-driven resource): mnemonic → input/output/both, and per operand the role
  (read, write, read-write, instance, routine, expression, length, literal-only) and type (TIMER, COUNTER, CONTROL,
  MESSAGE, PID, …). It covers the top instructions by repo count (expected ~80, chosen from the corpus as in M4) and
  is checked against the Logix 5000 General Instructions Reference Manual (1756-RM003). A mnemonic that isn't in the
  table and isn't an AOI in the project becomes an `UnknownInstruction` call: its operands count as *possibly
  written*. Rules then neither invent a double coil nor miss a write by guessing.
- New AST nodes (`plc-ast`, the "Ladder IR" of CLAUDE.md):
  - `Statement.Rung(number, comment, ladder, lowered, span)`, a container like `Region`. Rules see the lowered
    statements through `statementsDeep()`.
  - `Ladder` (series/branch/instruction tree with spans) stays on the rung for the M9 ladder viewer and for
    rung-specific rules. Every lowered node's span points at its instruction or operand.

### 5. Project model mapping (AST and semantic model)
| Rockwell | AST / semantic model | Analogy already in the model |
|---|---|---|
| Controller tags | one global container | GVL |
| Program | `Pou(PROGRAM)`; program tags are its `VAR` | PROGRAM |
| Routine | new `PouKind.ROUTINE`: no own variables, shares its program's (or AOI's) scope, called by JSR | CODESYS ACTION |
| Main / fault routine | program entry / extra entry point | program body |
| AOI | `Pou(FUNCTION_BLOCK)`: Input/Output/InOut parameters → `VAR_INPUT/OUTPUT/IN_OUT`, local tags → `VAR`, implicit `EnableIn`/`EnableOut`; Logic = body, Prescan/Postscan/EnableInFalse = members | FB with methods |
| UDT (`DataType`) | `STRUCT`; `BIT` members with `Target`/`BitNumber` = overlay on the hidden host | SCL `AT` overlay |
| Alias tag (`AliasFor`) | overlay variable: reads and writes count on the base tag | SCL `AT` overlay |
| Module I/O tags (`Local:1:I`) | `IoTagSymbol` (area I/O/C, module name). Its type comes from the module definition when it is exported; otherwise external | Siemens external tag |
| Produced / consumed tags | global with a `produced`/`consumed` flag (consumed = written from outside) | — |
| `ExternalAccess` | `Read/Write` = HMI-writable, `Read Only`, `None` | Siemens `ExternalAccessible` |
| Tasks | `TaskModel` with **real** type, priority and rate; event tasks keep their trigger | `.TcTTO` tasks |
| Safety program/tag (`Class="Safety"`) | flag on POU/variable; rules can use it (M7) | — |
| Encrypted routine / AOI (`EncodedData`) | interface kept if present; body skipped with a diagnostic | know-how-protected SCL |

Rockwell is the first dialect whose export always contains the task configuration, so the M7 race rule will have
real data here.

### 6. Findings point to what the engineer sees
Studio 5000 shows *program → routine → rung n*, not XML lines. Every finding keeps its physical location in the
`.L5X` (the CDATA line). Its SARIF `logicalLocations` / console output adds the Rockwell path:
- `Program:Main/Routine:R02_Conditions/Rung:14` for rungs;
- the line inside the routine for ST.

The existing `f.pou()` logical location becomes a structured path (kind per segment). The other dialects keep their
current output.

### 7. FBD, SFC and L5K
- **FBD (143) and SFC (65) routines**: skipped with an info diagnostic in M5. M6 builds the graph lowering for
  PLCopen LD/FBD/SFC, and the L5X FBD sheets can then reuse it.
- **L5K** (42 files, text format): out of scope. The CLI keeps listing it as skipped.

## Rules on ROCKWELL
All ten M3 rules declare `ROCKWELL`, with fixtures in `plc-rules/src/test/resources/<id>/rockwell/`:
- **P001 double coil**: OTE of the same tag in more than one rung or routine (alias-resolved). This is the headline
  ladder check. Set/reset pairs and the startup/first-scan exemption work as before (`S:FS` first-scan bit).
- **Q001 unused**: tags with `ExternalAccess = Read/Write` or `Read Only` count as HMI-accessible and aren't
  reported, like Siemens statics. AOI parameters and local tags, program tags with `None`, and unused UDT/AOI
  definitions are reported.
- **P002 direct addressing**: depends on the module I/O decision (below).
- **Q003, Q004**: also on EQU/NEQ with REAL operands and DIV/MOD/CPT by zero in rungs.
- **Q006**: writing an AOI `Input` parameter inside the AOI logic.
- **Q007 recursion**: JSR cycles.
- **Q002, Q005**: ST routines only.
- **S001**: ST string literals, plus string tag initial values.

FP review: 20 Rockwell samples per rule, with the same ≤ 20% bar as M3/M4.

## Tests
- Grammar notes first. Then rung lexer/parser tests (branches, nesting, `?`, bit/index/module paths, expression
  operands, empty rungs), Rockwell ST lexer tests, and AST goldens per feature in
  `frontend-l5x/src/test/resources/golden/`.
- Lowering goldens: rung text → printed lowered statements. One table-driven test per instruction-table entry,
  plus nested branches with mid-rung outputs.
- Reader tests:
  - hand-written L5X fixtures for each `TargetType`, aliases, BIT members, AOIs, tasks, encrypted parts;
  - the XXE / truncated / bad-UTF-8 cases: a diagnostic, never an exception, never a network or file access;
  - span tests showing that findings land on the right CDATA line and the right ST editor line.
- Semantic golden: a hand-written controller project with two tasks, programs with JSR trees, an AOI with
  parameters, a UDT with BITs, alias tags, module I/O and a double coil across routines.
- Jazzer: `L5xFrontendFuzzTest` (XML + rungs + ST + model + rules) and a raw `RungParser` target.
- All fixtures are hand-written (owned by us). Corpus files are used only by the corpus check, following the licence
  policy (most permissive L5X files are generator output anyway).

## Corpus check and performance
- `:plc-devtools:corpusCheck` adds a **Rockwell group** (repo-weighted, with its own baseline). It reports:
  - XML read rate;
  - rung parse error-free rate and ST routine error-free rate;
  - SLL-fallback rate (≤ 2%);
  - share of instruction uses covered by the table vs AOI vs unknown;
  - name resolution (resolved / I/O / external / unresolved);
  - rule statistics;
  - peak heap on the largest file.
- **Target**: repo-weighted error-free ≥ **97%** of rungs and ≥ **95%** of ST routines. Rung text is
  machine-written by Studio 5000, so failures should be rare and every remaining one explained.
- JMH: `RungParseBenchmark` (two-stage vs LL) and `L5xLoadBenchmark` (whole file: StAX + rungs + lowering). Target:
  ≥ 1M rungs in < 10 s on one laptop (on par with the ST lines/s target).

## Decisions (2026-10-19)
All three recommendations approved: P002 option A, `$rcN` only where needed, FBD/SFC/L5K deferred as proposed.

The questions as asked:
1. **Module I/O tags and P002.** Rockwell has no `%I/%Q`. The closest equivalent is logic that uses raw module tags
   (`Local:1:I.Data.5`) instead of alias or mapped tags. Options:
   - **A (recommended)**: P002 reports module I/O references in logic, except in routines that are pure I/O mapping
     (every rung of the form `XIC(io)OTE(tag)` / `MOV(io,tag)` or the reverse). That is the usual "map I/O in one
     place" convention.
   - B: report every module I/O reference.
   - C: P002 doesn't apply to ROCKWELL.
2. **Power-flow temporaries**: synthetic `$rcN` only where needed (recommended, as in decision 4), or always one
   per rung. The first gives more readable goldens; the second gives simpler lowering code.
3. **FBD/SFC routines** wait until after M6, and **L5K** is out of scope. OK?

## As built (2026-10-19)
- **Modules**: `frontend-l5x` (`L5xReader` StAX over the decoded text, DTD/external entities off via the shared
  `XmlInput`; `RungLexer`/`RungParser`; `RockwellStLexer`/`RockwellStParser` on the shared core; `RungLowering`;
  `AoiCalls`; `L5xFrontend`). `plc-ast`: `Ladder` IR, `Statement.Rung`, `PouKind.ROUTINE`, `Identifier.Form.PROGRAM`
  and `SYNTHETIC`, `Expression.IndirectBit`, `AssignOp.NON_RETENTIVE`, the `StText` printer and the instruction table
  (`dev.plca.ast.ladder.InstructionSet`, ~120 instructions from RM003; entries not checked against the manual text are
  marked `?`). Notes: `docs/grammar/rockwell.md`.
- **Deviation from the plan**: expression operands are parsed by the rung grammar's own small expression rules, not by
  a second parse with the ST grammar — one parse per routine instead of one per operand (millions of operands in the
  corpus). The rules mirror the ST precedence; the lowering goldens cover them.
- **Lowering** (decision 2): a condition DAG; `$rcN` only where a non-trivial condition is reused, where a side effect
  must stay in order, or where an output writes a tag the condition reads. Branches are built relative to their root
  (`A AND (B OR NOT C)`); consecutive conditional outputs share one `IF` (the rung condition is computed once); unknown
  instructions stay in the condition. AOI calls become FB calls (`tag(Cmd := a, Open => b, EnableIn := cond)`) in rungs
  and ST, using the operand order verified from the corpus (§9.7 of the notes).
- **Semantic model**: Rockwell instructions as `InstructionSymbol` (effects from the operand roles; unknown
  instructions give `UNKNOWN` accesses — a use, never a write), module and status tags as `IoTagSymbol`, aliases linked
  to base + path (and to I/O points), TIMER/COUNTER/CONTROL/STRING, `\Prog.Tag`, setting words in instruction
  operands, partial exports' unknown names as external, JSR/fault routine/AOI scan modes as call edges, tasks with
  real type, priority and rate.
- **Reports**: findings carry `place` (`Program:Main/Routine:Fill/Rung:14`, `…/Line:3` for ST, `AOI:Valve/…`), shown
  in the console and used as the SARIF logical location; fingerprints still use the POU name (rung numbers shift).
  The CLI reads `.L5X`; `.L5K` is listed as skipped.
- **Corpus** (§10 of the notes): rungs 99.57% and ST routines 99.45% error-free repo-weighted (targets 97% / 95%); no
  clean SLL fallback; names 98.36% resolved+library+external repo-weighted. The CODESYS/TwinCAT/Siemens rates are
  unchanged. Baseline keys added for L5X, L5X-rungs, L5X-st and Rockwell names.
- **Rules on ROCKWELL** (fixtures under `plc-rules/src/test/resources/<id>/rockwell/`), FP review on 20 samples each
  (generated benchmark repos dominate the occurrence counts, so samples were also judged per distinct case):
  - P001: 4/20 before the last fixes (unknown instruction treated as output, JMP/LBL loops, scratch/trash tags), each
    cause fixed; earlier rounds removed AOI scan-mode routines, non-coil writes across routines and AOI outputs bound
    to scratch tags. 217k findings in 69 projects, almost all in the generated `l5x-lint` benchmark files.
  - Q001 0/20; Q002 0/10; Q004, Q005, Q007 0; S001 2/10 → fixed (punctuation-only literals).
  - Q006: 3/20 (an AOI writing a validated setpoint back to its HMI input); constant writes to AOI inputs (command
    clear, defaulting) are exempt.
  - P002: 5/20 before exempting whole module tags passed to device AOIs; now 0/20 against the option-A definition.
  - **Q003: about 30% of distinct cases are still deliberate** — sentinel checks (`NEQ(P_HighHigh,EUMax)` meaning
    "limit disabled"), a machine-epsilon loop, two settings compared where one is written by the AOI. Copy comparisons
    and comparisons of two unwritten tags are exempt (28,397 → 638 findings). **Above the 20% bar**; see follow-ups.
  - Shared changes: P001 now opens SCL `REGION`s (writes inside regions were invisible; Siemens P001 230 → 314, samples
    checked: real); Q003's copy exemption and Q001's "base used through an overlay is used" apply to all dialects.
- **Performance**: JMH `L5xLoadBenchmark` (whole frontend, one thread), generated controller with 100k rungs: 894 ms
  two-stage vs 1,015 ms LL-only (≈ 112k rungs/s; 1M rungs ≈ 9 s on one core). The 43 MB `bench_50mb.L5X` (≈ 330k
  rungs) loads in 3.2 s and retains 424 MB (≈ 1.3 KB per rung). No separate `RungParseBenchmark`: it would need the
  frontend's package-private parser classes, and the load benchmark's two-stage parameter measures the same gain.
- **Fuzzing** (5 min each, no failures): `fuzzL5x` 585k runs, `fuzzRungs` 620k runs, `RulesFuzzTest.fuzzL5xRules`
  668k runs.
- **Bugs found on the corpus and fixed**: exponential side-effect walk on nested branches; quadratic rung lookup for
  finding places; per-routine recomputation in Q003; rungs with errors kept half-recovered drawings (the rung rate was
  overstated until fixed); an unterminated rung text swallowed the next rung.

## Follow-ups
- Q003 on Rockwell: a sentinel/limit heuristic or a lower default severity for ladder; decide with the M7 rule config.
- Memory: ~1.3–2 KB retained per rung (spans and records); worth a look before the LSP (M8) keeps models alive.
- One controller per model: the CLI puts every L5X of a directory into one model, so two exports of the same
  controller give duplicate symbols and cross-file double coils. Per-controller models (like the corpus check) would
  fix it.
- Verify the open format points (notes §9), the `?` entries of the instruction table, and `=>` in CMP.
- FBD/SFC routines after M6 (graph lowering); L5K; module profiles to type I/O tags.
