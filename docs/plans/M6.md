# M6 — PLCopen XML frontend incl. LD/FBD graph lowering

Status: **done 2026-10-19; approved 2026-10-19** (interfaces: CODESYS plain text when present; general `Network` graph IR; SFC IR plus lowering). Format notes will go in
`docs/grammar/plcopen.md` (written first, after approval).

## Goal
Read PLCopen TC6 XML exports (schema versions 2.0 `tc6_0200` and 2.01 `tc6_0201`) into the same `plc-ast`:
- data types, global variables, configurations/resources/tasks;
- POUs with their interfaces;
- ST bodies;
- **LD and FBD networks lowered to statements** (design rule 4): the graph form of what M5 did for rung text;
- SFC charts.

Then build the semantic model and run the rules on them unchanged where they make sense, validated against the 2,827
PLCopen files in the corpus. After M6, all four languages of CLAUDE.md go through one model.

## Key decisions

### 1. Frontend `frontend-plcopen` and file selection
- `.xml` is everyone's extension. The frontend reads a file only if the first 4 KB name a PLCopen TC6 namespace
  (`tc6_0200`, `tc6_0201`; `tc6_0100` if it shows up). Any other XML is skipped silently (no diagnostic: a project
  folder is full of unrelated XML). This replaces the CLI's "skipped" listing for PLCopen.
- StAX skeleton reader on the decoded text, as in M5: shared `XmlInput` (no DTDs or external entities), offsets only;
  text decoded later by `XmlText` with exact spans.
- `Dialect.PLCOPEN` on the unit, with the producer (`companyName`/`productName`) as a unit attribute, so a rule can
  tell a CODESYS export from a Beremiz one later if it needs to.
- Corpus check: one project per file, as for L5X (a PLCopen file is a complete exchange unit, and repos keep many
  versions of the same project side by side).

### 2. Declarations and ST bodies
- ST bodies are parsed with the **CODESYS ST grammar** (`statementsOnly`). It is a superset of IEC ST, and the
  producers that matter are CODESYS-based; Beremiz/OpenPLC write plain IEC ST, which it also accepts. No new ST
  dialect grammar.
- Interfaces (**decision needed**). CODESYS exports carry the declaration twice: the structured `<interface>` of the
  standard and, in addData, `InterfaceAsPlainText`, the POU header and VAR blocks as source text (346 files /
  50 repos). Options:
  - **A (recommended)**: take the plain text when present and parse it with the CODESYS `declarationPart` rule,
    exactly like TwinCAT `<Declaration>`. It is the engineer's source, with pragmas, attributes, access modifiers,
    EXTENDS/IMPLEMENTS and comments, which the structured form drops or moves into addData. Fall back to the
    structured interface otherwise.
  - B: always use the structured interface, and read OOP and attributes from the matching addData.
  - Either way, spans point at whichever form was used.
- CODESYS methods, properties, actions and transitions, both in addData and in the standard `<actions>` and
  `<transitions>`, become POU members, as in the TwinCAT frontend.
- Types (`<dataTypes>`: struct, enum, array, subrange, derived, pointer/reference), `<globalVars>`, and
  `<configurations>` with resources, tasks and pouInstances map onto the existing AST (`TypeDecl`, `GlobalVars`,
  `Configuration`). CODESYS `tasksettings` addData supplies task priority and interval where the standard elements
  are empty.

### 3. Graphical bodies: graph IR plus lowering (**decision needed**: IR shape)
LD and FBD in PLCopen are **graphs**: nodes with a `localId`, and connections `refLocalId` (plus `formalParameter`)
from inputs back to outputs. Unlike L5X rung text, they are not guaranteed to be series-parallel: bridges and
feedback are legal. Options:
- **A (recommended)**: a new `plc-ast` **`Network` IR**: nodes (contact, coil, rail, block, in/out/inOut variable,
  connector/continuation, jump/label/return) with kind, attributes, position, the connections, and the span of the
  node's element. It is general enough for the M9 viewer to draw PLCopen LD/FBD as authored. A body is a list of
  `Statement.Network(number, network, lowered, span)`, the graph counterpart of `Statement.Rung`. The rules see the
  lowered statements.
- B: force LD into M5's `Ladder` (series-parallel) IR and fall back to a graph only when that fails. This gives one
  viewer format, but two code paths and a lossy conversion.

**Lowering** (shared by LD and FBD), the same ideas as M5:
- **Networks**: LD networks are the connected components between the rails, numbered top to bottom. FBD networks are
  the CODESYS `network` grouping where present, else connected components.
- **Order**: `executionOrderId` where it is set. Otherwise topological order (a node after everything it reads),
  ties broken by position (y, then x), which is how Beremiz and OpenPLC execute.
- **Power flow (LD)**:
  - a contact ANDs its term onto the incoming flow; several connections into one input OR them;
  - a coil assigns: `x := flow`, negated `x := NOT flow`, set/reset `IF flow THEN x := TRUE/FALSE`;
  - an edge contact is a call of a synthetic edge builtin, with side effects and its own hidden state;
  - a block's EN takes the flow, and its ENO gives the flow after it.
- **Data flow (FBD)**:
  - a function block with `instanceName` becomes an FB call statement (`inst(IN1 := …)`), and its outputs are read
    as `inst.Q`;
  - a function becomes an expression (`ADD(a, b)` folded to `a + b` for the IEC operators, so the rules see
    arithmetic);
  - outVariables become assignments.
- **Shared values**: an output used more than once (or whose evaluation has side effects) goes into a synthetic
  `$fbdN`, like M5's `$rcN`. Every block is evaluated once.
- **Feedback** (a cycle through an inOut variable or a block): it is cut at the edge that closes the cycle, and that
  input reads the variable's value from the previous cycle, as IEC 61131-3 defines feedback. A cycle with nothing to
  read from gets a diagnostic.
- Jumps and labels lower to `Jump`/`Label`, and a `return` to `Return`, so the rules' control-flow handling applies.
- Spans: every lowered statement has the span of its node's XML element (the PLCopen equivalent of M5's
  instruction span); the place is `POU:Main/Network:3`.

### 4. SFC (**decision needed**)
3,327 bodies, but in 47 repos (mostly verification research and CODESYS demos). Options:
- **A (recommended)**: an `Sfc` IR, with steps (initial flag), transitions (source/target steps, condition as an
  inline ST/LD/FBD body or a reference to a transition member), action blocks (qualifier, duration, inline or
  referenced action) and divergences. It is lowered to guarded statements, the classic SFC-to-ST translation:
  - each step has implicit flags `Step.X`/`Step.T`;
  - N actions run under `IF Step.X THEN …`;
  - S/R actions set and reset a stored action flag;
  - P/P0/P1 use an edge;
  - transitions become `IF StepA.X AND cond THEN StepA.X := FALSE; StepB.X := TRUE; END_IF`, with divergences
    expanded.

  The rules then see what actions read and write, which is enough for double coil and unused variables, and the M7
  SFC rules get the IR. Timing qualifiers (L, D, SD, DS, SL) are kept on the IR and lowered as plain guarded calls,
  flagged in the notes.
- B: the SFC IR only, without lowering. Actions are then analysed as members (they are often separate actions
  already), but the step logic is invisible to the rules.
- C: postpone SFC to M7 and treat SFC bodies as unparsed, with a diagnostic.

### 5. IL
21 bodies in 16 repos: out of scope. The body is skipped with an info diagnostic, which also makes the POU "opaque"
for Q001 (as for FBD in M5).

### 6. Semantic model and rules
- The semantic model needs no new concepts beyond SFC step flags (implicit variables `X`/`T` per step, visible as
  `StepName.X` in the POU) and the synthetic edge builtin.
- All ten rules declare `dialects: all` already; PLCOPEN gets fixtures under `plc-rules/src/test/resources/<id>/plcopen/`.
  P001 treats LD coils the way M5 treats OTE (coil spans from the network IR).
- FP review: 20 samples per rule, same bar as before. Generated or research corpora are judged per distinct case.
- M5 follow-ups that touch the same code: the CLI keeps one model per directory (PLCopen exports are usually one file
  per project, so this does not get worse). The Q003 ladder question stays with M7's rule config.

## Decisions (2026-10-19)
All three recommendations approved: 1 A, 2 A, 3 A.

The questions as asked:
1. **Interfaces**: CODESYS plain-text declaration when present (A, recommended) or always the structured interface
   (B)?
2. **Graphical IR**: a new general `Network` graph IR (A, recommended) or forcing LD into the M5 `Ladder` IR with a
   graph fallback (B)?
3. **SFC**: IR plus lowering to guarded statements (A, recommended), IR only (B), or postpone (C)?

## As built (2026-10-19)
- **Modules**: `frontend-plcopen` (`PlcOpenReader` streams the file and hands one small element tree per unit to the
  translator; `PlcOpenFrontend`, `Expressions`, `Bodies`, `NetworkBuilder`, `NetworkLowering`, `SfcTranslator`).
  `plc-ast`: `Network` (graph IR) and `Sfc` IRs, `Statement.Network` / `Statement.Chart`. `frontend-st`: an
  `expressionOnly` entry rule in the shared core and the public `StTexts` facade (declarations, statement lists,
  expressions with the CODESYS grammar). Notes: `docs/grammar/plcopen.md`.
- **Decisions as implemented**: CODESYS `InterfaceAsPlainText` is parsed like a TwinCAT declaration when present
  (EXTENDS/IMPLEMENTS, attributes, comments come from it), the structured interface otherwise (decision 1). LD/FBD
  networks keep their graph and are lowered by demand from their sinks in execution order: power flow, FB calls once
  (`inst(IN := …)`, outputs as `inst.Q`), IEC functions as operators, `$fbdN` for shared values, feedback read from the
  previous cycle — a function in a loop keeps its previous value in a `$fbdN` (decision 2). SFC charts become the
  `Sfc` IR with transitions resolved to source/target steps through divergences and jump steps, lowered to guarded
  statements with implicit step variables `S.X`/`S.T`, stored-action flags and edge builtins (decision 3).
  Graphical transition conditions drawn in the chart are evaluated with the network lowering.
- **Reports and rules**: places `POU:Main/Network:2`, `POU:Main/Chart`, `POU:Main/Line:n`, members as
  `POU:FB/Method:M/…`; P001 treats LD coils (not set/reset) like M5's OTE. Rule fixtures under
  `plc-rules/src/test/resources/<id>/plcopen/`; semantic golden project `plcopen_mixer` (LD, FBD with feedback, SFC,
  two tasks). The CLI reads PLCopen `.xml` (others skipped silently); `plca` no longer lists PLCopen as skipped.
- **Corpus** (notes §10): graphical bodies 99.13%, ST bodies 95.39% repo-weighted (targets 95%); names 95.59%
  resolved+library (target 90%); no clean SLL fallback. Other dialects unchanged; baseline keys added.
- **FP review** (20 samples per rule; the corpus is dominated by copies of one PPU benchmark and a security-research
  dataset with deliberately injected faults, so cases were also judged distinct): P001 0/20 (many are the dataset's
  injected double coils, real by construction); Q001 0/20 (checked in the files); Q006 0/20 by the rule's definition
  (the PPU benchmark passes FB instances as inputs and clears input commands; the M3 behaviour for CODESYS is kept);
  P002, S001 0; Q003 about 3/12 deliberate (an OSCAT fraction check, a sentinel comparison), as for CODESYS in M3.
- **Performance**: JMH `PlcOpenLoadBenchmark` (whole frontend, one thread) on a generated export of 800 POUs
  (ST, LD with 25 rungs, FBD, SFC): 205 ms two-stage vs 336 ms LL-only (two-stage run noisy, ±400 ms). The largest
  corpus file (36 MB, MATLAB-generated, 301k embedded texts) loads in 3.2 s and retains 148 MB.
- **Fuzzing** (5 min each, no failures): `fuzzPlcOpen` 543k runs, `RulesFuzzTest.fuzzPlcOpenRules` 665k runs.
