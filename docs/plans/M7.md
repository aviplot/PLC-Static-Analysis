# M7 — Rest of the rule set, HTML report, `plca.yaml`, baseline and suppressions

Status: **approved 2026-10-19**, in progress. Decisions 2–4 as recommended; the rule list (decision 1) was left to
research, see "Rule-list research" below.

## Goal
- Bring the rule set from 10 to about 25 rules (CLAUDE.md "Initial rule set"), each written once for all four
  languages through the shared model and validated on the corpus per dialect.
- Add a self-contained HTML report.
- Configure rules from a `plca.yaml` file: selection, parameters, severity, per-dialect overrides.
- Let teams adopt the tool on existing code: a baseline (report only new findings) and suppressions (inline and in the
  config).
- Close the two questions left open in M5/M6: Q003 on ladder, and one model per Rockwell controller.

## New rules
Rule IDs continue the M3 scheme. PLCopen identifiers were checked against the official Coding Guidelines v1.0
(2016-04-20): the "Identifier: Rule …" lines of the PDF, not its table of contents. Descriptors cite ID and title only.

| ID | Rule | PLCopen | Kind | Facts used | Default |
|---|---|---|---|---|---|
| PLCA-Q008 | Unused POU: never called, instantiated, used as a type or scheduled. Only checked when the project has an entry point (a task, or a PROGRAM), so libraries stay silent | CP2 | Project | call graph, instance graph, types, task model | warning |
| PLCA-Q009 | Unreachable code: statements after RETURN/EXIT/CONTINUE/JMP in the same list; branches of `IF FALSE`/constant conditions; `WHILE FALSE` | CP2 | POU | constant evaluator | warning |
| PLCA-Q010 | Read before assignment (**decision 2**): a variable is read on some path before any write in the same call, and its value is then only the implicit default | CP3 | POU | intraprocedural definite-assignment analysis on the statement tree | warning |
| PLCA-Q011 | Implicit narrowing conversion: assignment, argument or initial value from a wider to a narrower type (`DINT` → `INT`, `LREAL` → `REAL`, real → integer) without a conversion function | CP25 | POU | expression types | warning |
| PLCA-Q012 | Loop without evident exit: `WHILE`/`REPEAT` whose condition reads nothing the body writes (directly or through called POUs) and with no `EXIT`/`RETURN` | — | POU | effects, call graph | error |

That makes 24 rules. "Timer/counter instance reused" (CLAUDE.md PLC list) is folded into P003: it is the same fact, and
two rules would double every finding. Each rule gets a descriptor (Markdown with examples, as in M3), positive and
negative fixtures for every dialect where its form differs (`<id>/`, `siemens/`, `rockwell/`, `plcopen/`), and a
corpus false-positive review: 20 samples per rule and dialect group, bar ≤ 20%, judged per distinct case where
generated or research corpora dominate.

## `plca.yaml`
Found at the root of the analysed directory, or given with `--config`. CLI options override it.
```yaml
rules:
  select: [all]                  # ids, categories (quality, plc, security) or all; default: the default set
  disable: [PLCA-Q014]
  severity: {PLCA-Q013: warning}
  parameters:
    PLCA-Q013: {maxNesting: 4, maxComplexity: 15}
    PLCA-Q015: {boolPrefix: "x"}
  dialects:                      # per dialect: codesys, twincat, siemens, rockwell, plcopen
    rockwell:
      severity: {PLCA-Q003: info}
      disable: [PLCA-Q015]
suppress:
  - rule: PLCA-P002
    path: "io_mapping/**"        # glob over display paths
  - rule: PLCA-Q001
    pou: "FB_Legacy*"
baseline: plca-baseline.json
fail-on: error
```
- Parsed with Jackson's YAML module (Jackson is already the JSON library). Unknown keys, rules, parameters or
  dialects are configuration errors (exit code 2, with the line), as for the CLI options today.
- `RuleConfig` grows severity overrides and per-dialect overrides. The engine resolves the configuration per POU
  dialect, so a mixed folder (L5X next to CODESYS) gets the right settings for each.
- **Default set**: all rules except the opt-in style rules (Q014 magic numbers, Q015 naming). `plca rules` shows
  which rules are on by default and their PLCopen ID.

## Baseline and suppressions
- **Baseline**: `plca analyze <dir> --write-baseline plca-baseline.json` records the fingerprints of today's findings
  (the M3 `Fingerprints` recipe: rule + POU + normalised line text + occurrence, line-number independent).
  `--baseline <file>` (or `baseline:` in `plca.yaml`) then reports only findings that are not in it. The console and
  HTML reports show the baselined count; SARIF marks them with `baselineState: unchanged` instead of dropping them, as
  SARIF 2.1.0 intends. The file is JSON, sorted and stable, so it diffs well under version control. Entries that no
  longer match are reported as "fixed" in the summary.
- **Inline suppressions**, close to the code, in every language's comment form:
  - `// plca-disable-next-line PLCA-Q003 reason…` and `// plca-disable-line …` (ST, SCL);
  - `(* plca-disable PLCA-P001 *)` … `(* plca-enable PLCA-P001 *)` for a region;
  - `{attribute 'plca-disable' := 'PLCA-Q001'}` on a declaration or POU (CODESYS/TwinCAT pragma);
  - Rockwell: a rung comment containing `plca-disable PLCA-P001` suppresses that rule on the rung (Studio 5000 has no
    line comments in ladder); a tag description with it suppresses findings on the tag's declaration;
  - PLCopen: the comment of a network or the documentation of a POU or variable.
  - A suppression without a rule id is rejected (diagnostic): suppressing everything hides too much.
- **Config suppressions**: rule + path glob and/or POU glob, for generated code and vendor libraries.
- Suppressed findings are counted, never silently lost: the summary says how many and why (inline, config,
  baseline). `--show-suppressed` lists them.

## HTML report (`--format html`)
- One self-contained file: inline CSS and a little JavaScript, no external resources and no telemetry, since customer
  code is sensitive.
- Summary: counts by severity, rule and file, the run statistics (files, lines, time, name-resolution rate), and
  suppressed/baselined counts.
- Findings grouped by file, then POU, each with:
  - rule, severity and message;
  - the place (`Program:Main/Routine:Fill/Rung:14`, `POU:Main/Network:2`);
  - the source lines around it (for XML exports: the decoded routine text or rung, not the raw XML);
  - related locations, and a link to the rule's help (embedded descriptor Markdown, rendered to HTML at build time).
- Client-side filters by severity, rule, dialect and text; works offline in any current browser. Golden-tested on a
  fixture project; size stays proportional to the number of findings, not the project.

## Open questions from M5/M6
- **Q003 on ladder** (decision 3): with per-dialect severities available, the shipped default makes Q003 `info` for
  ROCKWELL (ladder REAL equality is mostly sentinel and configuration checks, about 30% deliberate in the M5 review)
  and keeps `warning` elsewhere. Users can change it in `plca.yaml`.
- **One model per controller** (decision 4): the CLI builds one semantic model per Rockwell controller export
  (an L5X with `TargetType="Controller"`), plus one model for everything else in the directory. Partial exports
  (routines, AOIs, UDTs) join the controller model that defines their context names, else the shared one. Two versions
  of a controller in one folder then no longer produce duplicate symbols and cross-file double coils. Findings are
  merged; reports stay one per run.

## Tests
- Per rule: descriptor examples (checked by `DescriptorTest`, as in M3), fixtures per dialect with inline markers,
  and an expected-findings golden.
- Config: YAML parsing goldens (valid files, every error with its line), resolution per dialect, precedence of CLI
  over file.
- Baseline: write/read round trip; fingerprints stable under line moves; new/unchanged/fixed counts; SARIF
  `baselineState`.
- Suppressions: each comment form in each language, region on/off, rejected bare suppressions, counts in reports.
- HTML: golden of a small project's report (normalised timestamps), plus an HTML validity check in the test.
- CLI: end-to-end runs with `plca.yaml`, `--baseline`, `--write-baseline`, `--format html`, and the per-controller
  models (two copies of one controller in a folder give no duplicate-symbol diagnostics).
- `RulesFuzzTest` keeps running every rule on every dialect's fuzz input.

## Rule-list research (decision 1)
The owner asked for the rule list to be settled by research. Two public references were compared with the list above:

- **CODESYS Static Analysis** (the checker shipped with CODESYS and, as TE1200, with TwinCAT): its rule table with
  PLCopen mappings and the set CODESYS recommends for its own libraries
  (content.helpme-codesys.com, "LibDevSummary/static_analysis"). Every planned rule has a counterpart there, with the
  same PLCopen mapping where one is given: SA0001 unreachable code (CP2) ↔ Q009; SA0030/SA0031 unused objects (CP2) ↔
  Q008; SA0131 implicit narrowing conversions ↔ Q011; SA0150 metrics (CP9, off by default) ↔ Q013 (info); SA0105
  multiple instance calls (CP20) ↔ P003; SA0006 writes from multiple tasks (CP10) ↔ P004; SA0039 possible null pointer
  dereference ↔ P005; SA0022 possibly unassigned return value ↔ Q010; SA0040 division by zero ↔ Q004 (M3). This
  confirms the PLCopen IDs chosen above.
- **Top 20 Secure PLC Coding Practices** (ISA Global Cybersecurity Alliance / admeritia, v1.0, 2021): practice 8
  "Validate HMI input variables at the PLC, not just at the HMI" and practice 9 (validate indirections, catch
  fence-post errors) are the code-level practices a static analyzer can check. S002 therefore checks two sinks of an
  HMI-writable value used without a check: physical outputs, and **array indexes** (practice 9). Practice 6
  (plausibility of timer/counter values) is not statically decidable and stays out; S003 covers the "hidden logic"
  item of CLAUDE.md, which no vendor checker has.

Result: the 14 rules above are kept as listed; timer/counter reuse stays folded into P003 (SA0105 also treats it as one
check); Q014 and Q015 stay opt-in (CODESYS ships its naming conventions and metrics off by default, too). S002's sinks
gain array indexes.
