# M8 — Language Server + VS Code extension

Status: **approved 2026-10-19**, all decisions as recommended; in progress.

## Goal
- A language server `plc-lsp` (Eclipse LSP4J) over the existing frontends, semantic model and rules. No analysis logic
  of its own (CLAUDE.md M8).
- Features: live diagnostics (syntax, semantic, rule findings), go-to-definition, find references, hover, document
  outline, workspace symbols. Quick-fixes come later.
- Incremental: re-parse only the changed file, update the model, re-run affected rules. Target **< 200 ms from
  keystroke to diagnostics on a typical POU**.
- `editors/vscode/`: a thin TypeScript extension that starts the server, plus TextMate grammars for ST and SCL.
- All four input formats: `.st`, TwinCAT XML, `.scl/.db/.udt`, `.L5X`, PLCopen XML. Positions in XML files map to and
  from the embedded ST/rung text (design rule 5).

## What exists and what is missing
| Need | Have | Missing |
|---|---|---|
| Parse one file | `Frontend.parse(SourceFile, SourceRegistry, sink)`, one instance per thread | parsing from an editor buffer (only from disk via `ProjectLoader`) |
| Pipeline | `dev.plca.cli.Analyzer` (load → model groups → rules → baseline/suppressions) | lives in `plc-cli`; the LSP must not depend on the CLI |
| Definition | `SemanticModel.symbol(Expression)`, `Symbol.declaration()` with spans | node at an offset; the declared *name* span for every symbol kind |
| References | the same map, keyed by expression | an inverted index symbol → occurrences |
| Hover | `SemanticModel.type(e)`, `VariableSymbol` section, initialiser, attributes | a printer for a symbol's declaration line |
| Positions | `Span` offsets are UTF-16 code units = LSP default encoding; `SourceRegistry.resolve` maps fragment → file | the inverse **file → fragment** (`SourceMap` has only `toFileStart/End`), needed for a cursor inside CDATA/`<Text>` |
| Re-analysis | model build 9.7 ms and parse 27 ms per 18.6k lines (M2 JMH); rules ≈ 6 s CPU per 1M lines (M7) | a per-file unit cache and a registry that can replace one file's texts |

## Architecture
```
plc-core <- plc-ast <- plc-semantic <- plc-rules <- plc-report
                                                     ^
frontend-* ------------------------------------> plc-analysis   (new: Analyzer, ConfigFile, model groups, Workspace)
                                                  ^          ^
                                              plc-cli     plc-lsp  (new: LSP4J server; `plca lsp` lives in plc-cli)
```
- **`plc-analysis` (decision 1)**: `Analyzer`, `ConfigFile` and `modelGroups` move out of `plc-cli` unchanged. New
  in it: `Workspace`, the incremental state both the LSP and (in M9) the web backend use.
- **`Workspace`**: root path, config (`plca.yaml`, baseline), and per file `{version, SourceFile, SourceUnit,
  diagnostics}`. `update(path, text)` parses that file only, with a thread-local frontend. Open editor buffers
  override disk; file watcher events (`workspace/didChangeWatchedFiles`) re-read closed files.
- **Registry per file version**: `SourceRegistry` gets a `replace(path)` that drops a file's texts and frees their
  ids (or a generation per file); spans of other files stay valid. Old units are released, so a long session does
  not leak (design rule 7: no parse trees are kept anyway).
- **Two-tier analysis per change** (decision 2):
  1. *Fast tier*, after a 100 ms debounce: re-parse the file, rebuild the model of that file's model group from cached
     units, run **POU rules on the POUs of the changed file only**, publish diagnostics for that file. Budget 200 ms.
  2. *Project tier*, after 750 ms idle or on save: all rules of the group (project rules: unused POU, double coil,
     cross-task writes, …), publish diagnostics for every file whose set changed. Cancelled and restarted by the
     next edit (a version counter, checked between POUs and between rules).
  If model rebuild on large groups exceeds budget, the follow-up is a model that rebinds only changed POUs; we
  measure before building it (JMH `EditCycleBenchmark`, below).
- **Queries** run on the last complete model snapshot (immutable, so no locks): `NodeIndex` (offset → innermost
  expression/declaration per unit, built lazily, binary search over sorted spans) and `ReferenceIndex` (symbol →
  expressions, built lazily per model from `SemanticModel.symbols`; needs a package-visible accessor or a
  `forEachBinding` on the model).
- **Threads**: LSP4J message thread only enqueues; one analysis thread owns the `Workspace`; queries use snapshots;
  rule parallelism uses the existing pool (`threads` = cores − 1).

## Features
| LSP request | Behaviour | Notes |
|---|---|---|
| `publishDiagnostics` | PLC-SYN/SEM/XML diagnostics and findings; severity mapped (error/warning/info → Error/Warning/Information); `code` = rule id with `codeDescription` link to the rule doc; suppressed and baseline findings not shown (decision 3) | `relatedInformation` for findings with several places (double coil) |
| `definition` | name → declaration name span: variables, POUs, methods/actions/properties, types, enum values, GVL members, Rockwell tags/UDT members/AOIs, Siemens `"DB".member` and `#local` | builtins and library symbols: none (no source) |
| `references` | all bound occurrences in the snapshot, with `includeDeclaration` | member accesses through instances count (`fb.x` → `x`) |
| `hover` | Markdown: declaration line (`VAR_INPUT bStart : BOOL := FALSE;`), owner POU, attributes, the doc comment directly above; for an expression its type; for a builtin its signature | |
| `documentSymbol` | hierarchical: POU → var blocks → variables, methods, actions, properties; types and members; GVLs; L5X: programs → routines, tags, UDTs, AOIs; PLCopen: POUs, types, configuration/tasks | `SymbolKind` mapping table in the module doc |
| `workspace/symbol` | POUs, types, global variables, tasks; case-insensitive prefix + camel-hump match | from all groups |
| `didChangeConfiguration` / watched `plca.yaml` | reload config, project tier for all | |
| Commands | `plca.analyzeWorkspace`, `plca.showRuleDoc` | |

Text sync: **full** document sync in v1 (decision 4). XML exports are edited rarely; L5X files over a limit (default
20 MB) are analysed from disk only and never synced (VS Code does not sync files over 50 MB either).

## VS Code extension (`editors/vscode/`)
- TypeScript, `vscode-languageclient`, esbuild bundle; language ids `iec-st` (`.st`, `.TcPOU`/`.TcDUT`/`.TcGVL`/`.TcIO`
  as XML documents with diagnostics on them), `siemens-scl` (`.scl`, `.db`, `.udt`), and diagnostics on `.L5X` and
  PLCopen `.xml` (detected by namespace, not extension).
- Starts `plca lsp` over stdio. Java: setting `plca.java.home`, else `JAVA_HOME`, else `java` on the path, version
  check ≥ 21 with a clear message (decision 5: no bundled JRE in M8).
- The server jar is shipped inside the VSIX (`installDist` output copied by a Gradle task); `./gradlew :editors:vscode:package`
  builds a `.vsix` via `npx @vscode/vsce`. Node is a build dependency only for this task, not for `./gradlew build`
  (CI gets a separate job).
- TextMate grammars `st.tmLanguage.json`, `scl.tmLanguage.json`: case-insensitive keywords, nested `(* *)`, pragmas,
  typed literals (`T#1s`, `16#FF`, `DT#…`), `%IX0.0`, Siemens `"quoted"`/`#local`, REGION. Injection grammar for the ST
  inside TwinCAT CDATA. Tests: `vscode-tmgrammar-test` snapshots on files from our grammar fixtures.
- Settings: `plca.java.home`, `plca.config` (path to `plca.yaml`), `plca.trace.server`, `plca.maxFileSizeMb`.

## Tests
- `plc-lsp`: JUnit tests that drive the server in-process through LSP4J's `Launcher` on piped streams: open/change/
  close, diagnostics per tier, every request on fixtures of all four languages (golden JSON of the responses), XML
  position round-trips (cursor in CDATA, in L5X `<Text>`, in an `&lt;`-escaped region).
- `SourceMap` inverse: property test, `toFragment(toFileStart(o)) == o` for every offset of the fixtures and corpus
  samples.
- Robustness: Jazzer target sends random edit sequences (insert/delete at random offsets) and random requests; the
  server never throws and never publishes diagnostics for a stale version.
- **JMH `EditCycleBenchmark`**: one-character edit in a POU of the 18.6k-line generated project and of the largest
  corpus project per dialect; fast tier and project tier separately. Pass mark: fast tier p95 < 200 ms on the
  generated project.
- Extension: a `@vscode/test-electron` smoke test (open fixture, wait for one diagnostic, go to definition) in the CI
  job with Node; grammar snapshot tests.

## Deliverables
1. `plc-analysis` module (move), `SourceMap` inverse, `SourceRegistry.replace`, `SemanticModel` binding accessor.
2. `plc-lsp`: `Workspace`, analysis scheduler, `NodeIndex`, `ReferenceIndex`, the six features, `plca lsp`.
3. `editors/vscode/`: extension, TextMate grammars, packaging task, smoke test.
4. JMH `EditCycleBenchmark`, fuzz target, docs `docs/lsp.md` (setup, settings, feature matrix per language).
5. "As built" in this file.

## Decisions needed
1. **Shared pipeline module.** (a) New `plc-analysis` with `Analyzer`/`ConfigFile`/`Workspace`; `plc-cli` and
   `plc-lsp` both depend on it — **recommended**: M9's web backend needs the same thing. (b) `plc-lsp` depends on
   `plc-cli` — inverts the dependency direction in `settings.gradle.kts`.
2. **Incrementality.** (a) Two tiers as above, file-granular re-parse, full model rebuild per group, measured first —
   **recommended**: the M2 numbers suggest the rebuild fits the budget for typical projects, and it keeps one model
   builder. (b) Fine-grained incremental model (rebind only dependents of changed declarations) now: large, and only
   needed if the benchmark says so.
3. **Baseline and suppressions in the editor.** (a) Respect `plca.yaml`, inline suppressions and the baseline exactly
   as the CLI does — **recommended**: the editor and CI must agree. (b) Ignore the baseline in the editor (show
   everything); (c) show baselined findings as `Hint` with an "in baseline" tag.
4. **Text sync.** (a) Full sync in v1 — **recommended**: we re-parse the whole file anyway; the cost is sending the
   text, small for POU files. (b) Incremental sync now.
5. **Java runtime.** (a) Require Java 21+ on the machine, configurable path — **recommended** for M8. (b) Ship a
   jlink'd runtime per platform in platform-specific VSIX files (≈ 40 MB each) — better for controls engineers
   without Java; can be added in M9 alongside the web backend packaging.

Versions (LSP4J, `vscode-languageclient`, `@vscode/vsce`) are checked against Maven Central / npm at the start of the
implementation and pinned in `libs.versions.toml` / `package-lock.json`.
