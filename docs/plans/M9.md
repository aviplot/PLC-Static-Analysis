# M9 — Web workbench ("PLC code review workbench")

Status: **approved 2026-10-20**, decisions 1–6 as recommended.

## Goal
- A browser workbench for reviewing a PLC project export: open a folder or zip of `.st`, TwinCAT files, `.scl/.db/.udt`,
  `.L5X` or PLCopen XML; file tree; Monaco editor with highlighting and the M8 language features; findings panel with
  filtering by rule/severity and click-to-navigate (CLAUDE.md M9).
- **Ladder viewer**: L5X rungs and PLCopen LD (and FBD, which costs little extra) as SVG from the IRs we already keep,
  read-only, with findings highlighted on the element that carries them.
- **Diff view** between two versions of a project: file diffs plus new / fixed / unchanged findings.
- Backend: a small Java web server hosting the M8 language server over WebSocket, plus upload and project endpoints.
  No analysis logic of its own, as in M8.
- Uploaded code is sensitive: no third-party requests or telemetry, uploads deleted at session end by default.
- Out of scope (CLAUDE.md): compiling, download to a PLC, online/monitoring, hardware configuration. Also out: user
  accounts, editing graphical languages, SFC rendering (follow-up).

## What exists and what is missing
| Need | Have | Missing |
|---|---|---|
| Live analysis | `plc-analysis` `Workspace`/`Snapshot`, `plc-lsp` `Session` (two tiers, generations), all over a root directory | an LSP endpoint over WebSocket; a root that is a temporary upload directory; URIs that do not reveal server paths |
| Navigation | definition, references, hover, outline, workspace symbols on all four languages | — |
| Findings with metadata | `RuleDescriptor`, `plca.ruleDoc`, JSON report (`docs/report-json.schema.json`) | a request that lists rule metadata for the panel's filters |
| New vs fixed | `Fingerprints` (line-independent), `Baseline` (match / "fixed" entries) | comparing two analyses rather than an analysis and a file |
| Rung drawing | `Ladder` (series/parallel elements with spans) on every `Statement.Rung` | rung comments (L5X `<Comment>` per rung is not in the IR; `TODO(verify-format)` on its exact place); a layout and an SVG renderer |
| LD/FBD drawing | `Network.Element` with `x`, `y`, pins and links | element `width`/`height` and pin `relPosition` (the PLCopen reader skips `relPosition`), so wires cannot be drawn where the author drew them |
| Highlighting | TextMate grammars generated by `editors/vscode/scripts/grammars.py` | Monarch tokenizers (Monaco does not run TextMate without extra machinery) |

## Architecture
```
plc-analysis <- plc-lsp <- plc-web (new: Jetty server, WebSocket LSP, upload/project API, ladder/network SVG endpoint)
                              ^
plc-report (+ LadderSvg, NetworkSvg)          plc-cli: `plca web`
editors/web/  (new: TypeScript frontend, built by npm, bundled into plc-web's jar as static resources)
```
- **`plc-web`** (decision 1): embedded **Jetty 12** with the Jakarta WebSocket container and LSP4J's
  `org.eclipse.lsp4j.websocket.jakarta` endpoint. One `PlcaLanguageServer` + `Session` per WebSocket connection, each
  with its own `Workspace` rooted at the project's upload directory. Static files, REST and WebSocket on one port.
- **URIs**: the browser sees `file:///project/<display path>`; `plc-web` maps this prefix to the upload directory in
  `Convert`'s URI functions (a root URI passed in through `initializationOptions`), so server temp paths never reach the
  client and are not in diagnostics.
- **Projects**: `POST /api/projects` (zip, or a multipart folder upload from `<input webkitdirectory>`) → id; files are
  extracted into `$tmp/plca-web/<random id>/` (mode 0700), filtered by `Workspace.accepts` plus `plca.yaml` and the
  baseline file; everything else is dropped. `GET /api/projects/{id}/tree`, `GET …/files/{path}` (raw text for files
  too big for Monaco), `GET …/ladder?path=&pou=&routine=` and `…/network?…` (SVG, below), `GET …/report?format=json|sarif|html`
  (the same reports as `plca analyze`, for download), `DELETE /api/projects/{id}`.
- **Compare**: `POST /api/compare {base, head}` (two project ids) runs a full analysis of both through `Analyzer`
  and classifies findings by fingerprint: new (head only), fixed (base only), unchanged. File pairs: same display path;
  added/removed files listed. The frontend shows file diffs in Monaco's diff editor.
- **Lifecycle** (decision 4): a project belongs to the browser session that uploaded it (an HttpOnly, SameSite=Strict
  cookie). It is deleted when the session's last WebSocket closes and a grace period (default 2 min, for reloads)
  passes, after an idle timeout (default 30 min), on `DELETE`, and on server shutdown; leftovers of a crashed server
  are removed at startup. `--keep-uploads` turns deletion off for local use.
- **Limits**: upload size (default 200 MB), extracted size (1 GB), entry count (100k), compression ratio (zip-bomb
  guard), path normalisation (no `..`, absolute paths, symlinks or device names: zip-slip), concurrent projects per
  session (4). Files over `maxFileSizeMb` (20) open in a read-only plain viewer with diagnostics listed, as in the LSP.

## Frontend (`editors/web/`)
- TypeScript, **esbuild** bundle (as `editors/vscode`), UI in **Preact** (decision 3); Gradle project `:editors:web`
  whose output is copied into `plc-web`'s resources. Node is needed only for this task and a separate CI job, as in M8;
  `./gradlew build` stays Node-free by committing nothing generated and making `plc-web` serve a placeholder page when
  the bundle is absent.
- **Editor**: Monaco + `monaco-languageclient` over WebSocket (decision 2). Language ids as in VS Code (`iec-st`,
  `siemens-scl`, `twincat-xml`, `rockwell-l5x`, PLCopen by namespace). Monarch tokenizers generated by extending
  `grammars.py` so keyword lists have one source. Buffers are editable for trying a fix (live diagnostics through the
  LSP), never written back; "Download changed files" gives a zip (decision 5).
- **Layout**: file tree (filter, finding counts per file/folder) · editor tabs · findings panel (group by file or
  rule; filter by rule, severity, category, dialect, text; counts; baseline/suppressed hidden as in the editor) ·
  outline (from `documentSymbol`). Click on a finding opens the file at the span; for an L5X rung or PLCopen LD body it
  offers "show in ladder".
- **Ladder viewer**: a routine/POU at a time, rungs in a virtualised list (L5X routines with thousands of rungs).
  Elements carry `data-span`; hover shows the operand's hover (LSP `hover` at the span), click jumps to the text,
  findings draw a marker on the element whose span contains the finding's, with the message on hover.
- **Diff view**: pick two uploaded projects; summary (new/fixed/unchanged per rule), file list with change and finding
  deltas, Monaco diff editor with new findings marked on the head side and fixed ones on the base side.
- **Privacy**: all assets self-hosted (Monaco workers and fonts included); a strict CSP (`default-src 'self';
  connect-src 'self'`); no analytics. An e2e test asserts that no request leaves the origin.

## Ladder and network rendering (server-side, `plc-report`)
- **`LadderSvg`** (decision 6: server-side, so the HTML report can embed rungs later): recursive layout over
  `Ladder.Element` — a series is placed left to right, a branch's legs are stacked, width = max leg, height = sum of
  legs; outputs (`OTE/OTL/OTU`, boxes) right-aligned against the right rail as Studio 5000 draws them. Symbols:
  `XIC` ┤ ├, `XIO` ┤/├, `OTE` ( ), `OTL` (L), `OTU` (U), `ONS`/`OSR`/`OSF`, and a box with mnemonic and operand rows for
  everything else (timers, counters, math, MOV/COP, JSR, AOIs) using `InstructionSet` for operand names. Rung number and
  comment on the left. Text escaped; tag names elided with a `<title>` beyond a width.
- **`NetworkSvg`**: PLCopen LD/FBD at the author's coordinates (scaled), element boxes from the new `width`/`height`,
  wires as orthogonal polylines between pin positions from `relPosition`, connectors/continuations as labels, negation
  circles, execution-order badges.
- IR changes: `Statement.Rung` gets the rung comment; `Network.Element` gets `width`, `height` and per-pin relative
  positions (`frontend-plcopen` stops skipping `relPosition`). Golden AST tests updated.

## Tests
- `plc-web`: JUnit with Jetty on a random port — upload (zip, folder), zip-slip/zip-bomb/limit rejections, tree and
  files, LSP over a real WebSocket client (initialize, diagnostics, definition on all four languages), report
  downloads equal `plca analyze`, compare results on a fixture pair (golden JSON), lifecycle (directory gone after
  close + grace, idle timeout, startup sweep), cookie isolation (another session cannot read a project), URIs never
  contain the temp path.
- Rendering: golden SVG tests for every Rockwell and PLCopen fixture; a corpus check
  (`plc-devtools:renderCheck`) that renders every rung and network of the corpus — no exceptions, layout time per rung,
  and SVG well-formedness; spot-checked by eye against Studio 5000 / CODESYS screenshots in the docs for a few
  shapes (nested branches, empty legs, long outputs).
- Frontend: unit tests for the findings filter and the compare view model; **Playwright** e2e against `plca web`
  (upload the `plant` fixture, findings appear, filter, click navigates, hover, ladder renders with a highlighted
  finding, diff shows new/fixed, no external requests, project deleted after closing the page).
- Fuzzing: Jazzer target on the zip extractor (random archives never escape the directory or exceed limits).
- Performance: upload + first full analysis of the 24k-line generated project < 3 s; the largest corpus L5X opens its
  first routine's ladder in < 1 s; fast-tier diagnostics in the browser as in M8 (WebSocket adds < 10 ms locally).

## Decisions needed
1. **Web server.** (a) Embedded Jetty 12 + LSP4J's Jakarta WebSocket module — **recommended**: one dependency family,
   LSP4J already supports it, no framework. (b) Javalin (on Jetty, nicer routing, one more layer). (c) JDK
   `HttpServer` — has no WebSocket.
2. **LSP client in the browser.** (a) `monaco-languageclient` as the brief says — **recommended**, with the caveat that
   its current versions are built on `@codingame/monaco-vscode-api` (large bundle, VS Code service layer); I check
   size and that it makes no network calls before committing to it. (b) Plain `monaco-editor` + a thin own client for
   the six features we use (≈ 500 lines of TypeScript): smaller and fully under our control, but our own code to
   maintain. If (a) fails the size/privacy check I'd switch to (b) and tell you.
3. **UI framework.** (a) Preact — **recommended**: 4 KB, components for tree/panels/diff without a heavy toolchain.
   (b) Plain TypeScript DOM code. (c) React — same model as Preact, much bigger.
4. **Deployment and access.** (a) Local single-user tool by default: binds to `127.0.0.1`; binding elsewhere requires
   `--token` (or prints a random one, Jupyter-style), plus the session cookie — **recommended**; TLS and real user
   accounts via a reverse proxy, documented, not built. (b) Multi-user server with login now — needs an identity
   design the brief does not ask for.
5. **Editing.** (a) Editable buffers with live diagnostics, never saved; changed files downloadable as a zip —
   **recommended**: "try the fix" is cheap with the M8 server and stays a review tool. (b) Strictly read-only.
6. **Where ladders are rendered.** (a) Server-side SVG in `plc-report` — **recommended**: golden-testable in Java,
   reusable by the HTML report, one layout for all clients. (b) In the browser from a JSON IR — more interactive
   rendering, but layout code in TypeScript and no reuse in reports.

Follow-ups from M8 that M9 touches, **not** planned here unless you want them: the incremental semantic model (the
fast tier on very large groups), and a bundled Java runtime (jlink) — for `plca web` I'd ship the `installDist` zip
like the CLI. Third-party notices: Monaco (MIT), Preact (MIT), Jetty (EPL-2.0/Apache-2.0), LSP4J (EPL-2.0) go into a
`THIRD_PARTY_NOTICES` file served at `/about`.

Versions (Jetty, LSP4J websocket, monaco-editor, monaco-languageclient, Preact, Playwright) are checked against Maven
Central / npm at the start of the implementation and pinned in `libs.versions.toml` / `package-lock.json`.

## As built
- **Decision 2 switched to (b)**, as the plan allowed: `monaco-languageclient` 11.0.3 bundled to 13 MB minified
  (VS Code's workbench service layer, with strings for Copilot and extension-gallery endpoints) against 4.6 MB for the
  whole app with plain `monaco-editor` 0.57 and an own JSON-RPC client (`editors/web/src/lsp.ts`, ≈ 150 lines; the
  features are wired in `editor.ts`). Monaco 0.57's built-in LSP client was not usable: no custom requests, no
  initialization options.
- **Decision 1** as chosen, with one change: Jetty 12's core WebSocket API plus a 40-line bridge onto LSP4J's
  `RemoteEndpoint` (`LspSocket`), instead of LSP4J's Jakarta module, which would have pulled in the servlet (ee10)
  stack. SLF4J goes to java.util.logging; the `Server` header is off.
- **Versions**: Jetty 12.1.14, Preact 10.29.8 (11.0.1 was 12 days old and a new major), fflate 0.8.2, Atkinson
  Hyperlegible 5.3.0 (self-hosted), esbuild 0.28.2, TypeScript 7.0.2, Playwright 1.63.0 driving the installed Google
  Chrome (no browser download).
- **IR**: `Statement.Rung.comment`; `Network.Element` `width`/`height`, `Pin.at` (`relPosition`), `Link.route` (the
  `connection` points). PLCopen exports without sizes (CODESYS writes grid cells) get a layered layout by signal flow.
- **Drawings** (`plc-report`): `LadderSvg`, `NetworkSvg`, `Diagrams` (paged). `renderCheck` drew all 3,078,843 rungs and
  networks of 4,879 corpus files: 0 failures, p50 0.03 ms, p99 0.3 ms per part; the slowest routine (a synthetic
  50 MB benchmark file) takes 10 s whole, hence paging.
- **Language server**: `Uris` (file URIs, or `file:///project/…` mapped to the upload directory and confined to it),
  a sandboxed mode (config and baseline only from inside the root, the client's `config` option ignored, root paths
  masked in messages), `plca/diagrams` and `plca/diagram`.
- **Server**: as planned (`docs/web.md`). Fuzzing the extractor found a 500: an archive with a file `a` and an entry
  `a/b`; such entries are now skipped (regression seed kept). 2.49M runs in 5 minutes afterwards, no findings.
- **App**: review (tree, editor, findings punch list, outline), ladder/diagram view with findings outlined on the
  element and hover from the server, editable buffers with download of edited files, compare with Monaco's diff
  editor. Highlighting: Monarch tokenizers generated by `grammars.py` (TextMate output unchanged).
- **Tests**: `WebServerTest` (17), `ZipExtractorFuzzTest`, `UrisTest`, `DiagramsTest` (golden SVG, 4 fixture sets),
  app unit tests (10), Playwright (5: review, editing, ladder, compare, clean-up; no foreign requests).
- **Performance** (laptop): upload to full analysis shown 0.95 s (18k lines) and 1.4 s (184k lines). A real 43 MB L5X:
  first routine drawn 3.8 s after upload, **missing the 1 s target**: the time is the server's first parse of the whole
  file, the drawing itself takes milliseconds, and switching routines afterwards takes < 10 ms.
- Once, under a parallel full build, `LanguageServerTest` (M8) failed; it passed 5 reruns alone and a full
  `--rerun-tasks` build. Not reproduced; watch it.
