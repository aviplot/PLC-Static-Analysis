PLCA-Q001 Unused variable

Description

A local variable (VAR, VAR_TEMP, VAR_STAT, VAR_INST) is declared but never read or written by any code, initial value or declaration in the project.

Siemens SCL: static variables live in the instance DB, which HMIs and other PLCs may access, so they are reported only when the declaration hides them with { ExternalAccessible := 'False' }. Temporaries and constants are always checked; data block members are never reported.

Rationale

Unused declarations make a POU harder to read and suggest unfinished or dead logic; they also use memory. PLCopen Coding Guidelines rule CP24 Do not declare variables that are not used.

Not reported, because something outside the parsed code may use the variable: variables with an attribute pragma (HMI, OPC UA or ADS exposure), variables with an AT address (I/O mapping), names matching sparePattern, and every variable of a POU with a graphical or unparsable body. Inputs and outputs are interface, not locals, and are not checked here.

Rockwell (L5X): every tag carries ExternalAccess. Tags an HMI can read or write (Read/Write, Read Only) are not reported; tags with None are. A base tag used only through an alias tag counts as used.

PLCA-Q002 CASE without ELSE

Description

A CASE statement has no ELSE branch, so an unexpected selector value silently does nothing.

Rationale

State machines are usually written as CASE statements. If the state variable takes a value no branch handles (a new state, a corrupted value, a bad HMI write), the machine stops in an undefined state without any alarm. An ELSE branch makes that case explicit: raise an error or go to a safe state. PLCopen rule L17 asks the same for IF; the guidelines have no CASE rule, so no PLCopen id is given.

A CASE on an enumeration that handles every value is not reported by default.

Noncompliant

PROGRAM P_Sequence
VAR
    nStep : INT;
END_VAR
CASE nStep OF
    0: nStep := 10;
    10: nStep := 0;
END_CASE
END_PROGRAM

Compliant

PROGRAM P_Sequence
VAR
    nStep : INT;
    bFault : BOOL;
END_VAR
CASE nStep OF
    0: nStep := 10;
    10: nStep := 0;
ELSE
    bFault := TRUE;
END_CASE
END_PROGRAM
PLCA-Q003 Equality comparison of floating-point values

Description

A REAL or LREAL value is compared with = or <>.

Rationale

Floating-point values carry rounding errors, so a computed value is rarely exactly equal to another; the comparison may never become TRUE (a sequence that never advances) or flicker. Compare the difference against a tolerance instead. PLCopen Coding Guidelines rule CP8 Floating point comparison shall not be equality or inequality.

Comparisons with zero are not reported by default (CP8 lists them as its exception: a value set to 0.0 compares exactly), nor is x = x, the usual test for NaN.

A value compared with its own copy (IF a <> last THEN last := a;, ladder NEQ(a,last) MOV(a,last)) is change detection, exact by construction, and not reported. Rockwell (L5X): comparing two tags that no code of the program or AOI writes (EQU(Cfg_InpMax,Cfg_InpMin) to flag an empty range) compares settings and is not reported either.

Ladder (Rockwell) findings are info by default: in ladder, exact REAL comparisons are mostly sentinel and configuration checks. Raise them with dialects: {rockwell: {severity: {PLCA-Q003: warning}}} in plca.yaml.

Noncompliant

FUNCTION F_AtTarget : BOOL
VAR_INPUT
    rPosition : REAL;
    rTarget : REAL;
END_VAR
F_AtTarget := rPosition = rTarget;
END_FUNCTION

Compliant

FUNCTION F_AtTarget : BOOL
VAR_INPUT
    rPosition : REAL;
    rTarget : REAL;
END_VAR
F_AtTarget := ABS(rPosition - rTarget) < 0.001;
END_FUNCTION

PLCA-Q006 Write to a VAR_INPUT

Description

A VAR_INPUT of a function, function block or method is written inside that POU (or a method or action of it).

Rationale

Inputs are set by the caller on every call. Overwriting one inside the POU hides the caller's value, and the effect depends on whether the caller passes the input on the next call; for function blocks the changed value can also be read back from outside. Copy the input to a local variable and change that. PLCopen Coding Guidelines rule CP17 Usage of parameters shall match their declaration mode ("each input parameter should not be written"). Writes through a POINTER or REFERENCE input change the caller's data and are not reported.

Rockwell (L5X) Add-On Instructions: writing a constant to an input is a documented idiom — clearing a command an HMI or program set (OTU(PCmd_Start)), or replacing an invalid setting by a default (LEQ(Rate,0) MOV(1000,Rate)) — and is not reported; other writes are.

Noncompliant

    rRaw := 0.0;
END_IF

PLCA-Q007 Recursion

Description

A POU calls itself, directly or through a chain of other POUs (functions, methods, actions, FB bodies, property accessors).

Rationale

Each recursive call uses stack space, and PLC stacks are small and fixed; deep recursion can stop the controller. Support for recursion also differs between vendors, so the code is less portable. Replace the recursion with a loop. PLCopen Coding Guidelines rule CP13 POUs shall not call themselves directly or indirectly.

Cycles through a name that is declared more than once (overloaded methods in SIMATIC AX, duplicate copies of a POU) are not reported, because which declaration a call refers to is not known.

PLCA-P001 Double coil

Description

An output-like variable — a physical output (AT %Q…), a global variable, or the POU's own VAR_OUTPUT — is written unconditionally in more than one place, so only the last write of each cycle takes effect.

Rationale

This is the structured-text form of the ladder "double coil": two rungs driving the same coil. The earlier write is dead, the behaviour depends on execution order, and the logic that decides the output is spread over the application. Compute the value once, in one place. PLCopen Coding Guidelines rule CP12 Physical outputs shall be written once per PLC cycle covers physical outputs; this rule also checks globals and FB outputs.

To stay quiet on correct code, only unconditional writes count (:= or => in a top-level statement of a body), S=/R= latches, read-modify-write statements (n := n + 1) and writes inside IF/CASE/loops are ignored, and a second write in the same body is not reported when the variable is read in between (sequential use of a working variable).

In ladder (Rockwell L5X) an OTE is a coil by definition: it counts even when its rung reads the coil (seal-in) and whatever happens between two OTEs, for any tag — the "duplicate destructive bit" check Studio 5000's verification warns about. Across routines only OTE coils are compared, since routines are often called conditionally as alternatives; an AOI's Prescan/Postscan/EnableInFalse routines are never compared with its logic (they run instead of it), and outputs of AOI calls do not count (a required AOI output must be bound to a tag, often a scratch tag). Tags whose name matches sparePattern are exempt.

Noncompliant

PROGRAM P_Conveyor
VAR
    bStart : BOOL;
    bJog : BOOL;
    qMotor AT %QX0.0 : BOOL;
END_VAR
qMotor := bStart;
qMotor := bJog;
END_PROGRAM

Compliant

PROGRAM P_Conveyor
VAR
    bStart : BOOL;
    bJog : BOOL;
    qMotor AT %QX0.0 : BOOL;
END_VAR
qMotor := bStart OR bJog;
END_PROGRAM
PLCA-P002 Direct addressing in code

Description

A direct address such as %IX0.1, %QW4 or %MD10 is used in code instead of a symbolic variable.

Rationale

A bare address says nothing about what it is, makes the code depend on one hardware layout, and is easily missed when the I/O configuration changes. Declare a variable with AT %… once and use its name. PLCopen Coding Guidelines rule N1 Avoid physical addresses.

Siemens SCL: absolute operands (%I0.0, %DB1.DBX0.0, classic DB10.DBW2) and ANY pointers (P#DB1.DBX0.0 BYTE 10) are reported; use a PLC tag ("Start_Button") or a data block member ("DB_IO".Valve) instead.

Rockwell (L5X) has no direct addresses; the equivalent is logic on raw module tags (Local:1:I.Data.5, Rack1:2:O.Data[0]). They are reported except in routines that only map I/O (every rung a contact driving a coil, a MOV/COP, or every ST statement a plain assignment) and when a whole module tag is handed to a device AOI (PF755_Drive(Pump, Pump:I, Pump:O, …)), the device-object form Rockwell recommends. Alias tags of module points are the compliant form. Controller status flags (S:FS) are not I/O.

Noncompliant

PROGRAM P_Lamp
%QX0.1 := %IX0.0;
END_PROGRAM

Compliant

PROGRAM P_Lamp
VAR
    iButton AT %IX0.0 : BOOL;
    qLamp AT %QX0.1 : BOOL;
END_VAR
qLamp := iButton;
END_PROGRAM
PLCA-S001 Hard-coded credential or IP address

Description

A string literal is used as a password, token or other secret (assigned to, initialising, passed as or compared with a variable or parameter whose name matches namePattern), or a string literal is an IPv4 address.

Rationale

Credentials in the PLC program are visible to anyone who can read the project or upload it from the controller, cannot be rotated without a program change, and are often identical across machines. A password check against a literal is a back door. Hard-coded IP addresses tie the program to one network layout and hide communication partners from reviews. Keep secrets in a protected store and network settings in configuration.

Not reported: empty strings and masks such as '*****', loopback addresses and netmasks, and dotted numbers given to a version-like name (sVersion := '1.0.0.0', sFirmwareRev), which look like IPv4 addresses but are not.

PLCA-Q009 Unreachable code

Description

Code that can never run: statements after RETURN, EXIT, CONTINUE or JMP in the same statement list, an IF, ELSIF or WHILE whose condition is always FALSE, ELSIF/ELSE branches after a condition that is always TRUE, and Rockwell rungs disabled by an AFI instruction.

Rationale

Dead code misleads the reader, who must work out that it never runs, and often hides a mistake: a RETURN left over from debugging, or logic switched off with IF FALSE THEN and forgotten. PLCopen Coding Guidelines rule CP2 All code shall be used in the application.

Only conditions built from literals are reported by default. A condition on a named constant (IF cSimulation THEN) is usually a deliberate configuration switch; set includeNamedConstants to report those too. A label after a jump makes the following code reachable again. TwinCAT's RETURN(expression) is not treated as an unconditional exit. END_VAR

IF nValue > 100 THEN
    F_Limit := 100;
END_IF
END_FUNCTION

PROGRAM P_Test
VAR
    bPump : BOOL;
END_VAR
IF FALSE THEN
    bPump := TRUE;
END_IF
END_PROGRAM

    nValue : INT;

END_IF

PLCA-Q012 Loop without evident exit

Description

A WHILE or REPEAT loop whose condition is constant (WHILE TRUE, UNTIL FALSE) or reads only variables that the loop body never changes, and whose body has no EXIT, RETURN or JMP out of the loop.

Rationale

A PLC program runs inside a cyclic task: a loop that never ends keeps the cycle from finishing, the watchdog trips and the controller stops, with every output in its fault state. Waiting for an input inside a loop never works either — inputs are only read between cycles. Change the condition inside the loop, add an iteration limit, or restructure the wait as a step of a state machine that is checked once per cycle.

Not reported when the loop may end in ways the analysis cannot see: the condition calls a function, method or property or assigns a variable, reads through a pointer, reference or VAR_IN_OUT, or reads a global, an instance member or a function block instance while the body calls other code; or a variable it reads has its address taken anywhere in the POU.

Noncompliant

END_VAR

END_VAR
WHILE NOT bReady DO
    nTries := nTries + 1;

END_FUNCTION_BLOCK

Compliant

PLCA-Q013 Complex POU body

Description

A POU body nests IF, CASE, FOR, WHILE or REPEAT statements deeper than maxNesting, or its cyclomatic complexity is above maxComplexity. Complexity is 1 plus one for every IF/ELSIF condition, CASE branch, FOR, WHILE and REPEAT.

Rationale

Deeply nested and highly branched code is hard to read, review and test, and is where commissioning changes go wrong. PLCopen Coding Guidelines rule CP9 Limit the complexity of POU code. Description

A program, function block, function, class or Rockwell routine that nothing runs: it is not scheduled in a task, not called, not instantiated and not referenced from code that runs.

Rationale

Code that never runs still has to be read, reviewed and maintained, and a routine that was meant to run but is not called (a missing JSR, a program left out of the task) is a bug that testing on site may not reveal. PLCopen Coding Guidelines rule CP2 All code shall be used in the application.

Reachability starts at the entry points: the programs of the configured tasks and Siemens organisation blocks. PLCA-P003 Function block instance called more than once per cycle

Description

The same function block instance — a timer, counter, edge detector or user FB — is called more than once in a cycle: twice in one body (not as alternatives in different IF/CASE branches), or from two programs, function blocks or routines when the instance is global. Rockwell: the same TIMER in two TON/TOF/RTO instructions, or the same COUNTER in two CTU (or two CTD) instructions.

Rationale

A function block keeps state between calls and expects to be called once per cycle. A second call works on what the first left behind: a timer called with two different IN values restarts or never elapses, an R_TRIG sees no edge, a counter counts twice. In ladder the second timer instruction runs even when its rung is false, and resets the timer. PLCopen Coding Guidelines rule CP20 Function block instances should be called only once. Call the instance once and use its outputs where needed.

Not compared: calls inside loops, calls through a variable array index (afbAxis[i]()), calls in SFC actions, where the active step decides what runs, and tmr(IN := FALSE), the usual way to reset a timer when a state machine changes step. CTU and CTD on the same Rockwell counter form an up/down counter and are not reported. Rockwell Add-On Instructions are not compared: Logix has no functions, so stateless AOIs are routinely called several times.

Noncompliant

PROGRAM P_Conveyor
VAR
    fbDelay : TON;
    bStart, bStop, bRun : BOOL;
END_VAR
fbDelay(IN := bStart, PT := T#2S);
IF fbDelay.Q THEN
    bRun := TRUE;
END_IF
fbDelay(IN := bStop, PT := T#5S);
END_PROGRAM

Compliant

PROGRAM P_Conveyor

    fbStartDelay : TON;
    fbStopDelay : TON;
    bStart, bStop, bRun : BOOL;
END_VAR

fbStopDelay(IN := bStop, PT := T#5S);
IF fbStartDelay.Q THEN
    bRun := TRUE;
END_IF
END_PROGRAM
PLCA-P004 Global variable written from several tasks

Description

A global variable is written by code running in more than one task, according to the project's task configuration (IEC configurations, TwinCAT task objects, PLCopen instances, Rockwell tasks).

Rationale

Tasks of different priority interrupt each other. If two tasks write the same global, one task can preempt the other between reading and writing it, and an update is lost; a structure or string can be seen half written. PLCopen Coding Guidelines rule CP10 Avoid multiple writes from multiple tasks. Let one task own the variable and hand data over through separate variables, or use the runtime's synchronisation (CODESYS SysSem, TwinCAT TestAndSet).

The rule needs a task configuration with at least two tasks; without one it is silent. A POU runs in every task whose programs call it, directly or indirectly; Siemens organisation blocks are tasks. Startup tasks (startupTaskPattern, by default the TIA names of OB100–OB102) do not count, since they finish before the cyclic tasks start. One finding per variable.

Noncompliant

VAR_GLOBAL
    gnParts : INT;
END_VAR

PROGRAM P_Fast
gnParts := gnParts + 1;
END_PROGRAM

PROGRAM P_Slow
gnParts := 0;
END_PROGRAM

CONFIGURATION Cfg
    RESOURCE Res ON PLC
        TASK tFast(INTERVAL := T#2MS, PRIORITY := 1);
        TASK tSlow(INTERVAL := T#100MS, PRIORITY := 10);
        PROGRAM iFast WITH tFast : P_Fast;
        PROGRAM iSlow WITH tSlow : P_Slow;
    END_RESOURCE
END_CONFIGURATION

Compliant

VAR_GLOBAL
    gnParts : INT;
    gbResetParts : BOOL;
END_VAR

PROGRAM P_Fast
IF gbResetParts THEN
    gnParts := 0;
ELSE
    gnParts := gnParts + 1;
END_IF
END_PROGRAM

PROGRAM P_Slow
gbResetParts := TRUE;
END_PROGRAM

CONFIGURATION Cfg
    RESOURCE Res ON PLC
        TASK tFast(INTERVAL := T#2MS, PRIORITY := 1);
        TASK tSlow(INTERVAL := T#100MS, PRIORITY := 10);
        PROGRAM iFast WITH tFast : P_Fast;
        PROGRAM iSlow WITH tSlow : P_Slow;
    END_RESOURCE
END_CONFIGURATION
PLCA-Q010 Temporary variable read before assignment

Description

A temporary variable without an initial value is read on some path before anything assigns it. Temporaries are the locals of functions, methods and property accessors, VAR_TEMP of any POU, and a function's result.

Rationale

IEC 61131-3 sets every variable to its type's default before it is used, so nothing is ever undefined — but a temporary starts from that default on every call. Code that reads it first usually expects the value of the last call (which only a function block's static variable keeps) or forgot an assignment on one branch. On Siemens S7 classic (non-optimised) blocks, temporaries are not initialised at all and hold whatever the stack held. PLCopen Coding Guidelines rule CP3 All variables shall be initialized before being used.

The analysis follows the structure of the body: IF and CASE branches are merged, a loop body may run zero times (REPEAT at least once), and RETURN, EXIT and CONTINUE end a path. Passing the variable as VAR_IN_OUT or to a call whose parameters are not known (library code), taking its address or writing a part of it counts as an assignment. An accumulator that builds on the default (nSum := nSum + x, F := SHL(F, 1)) is deliberate in CODESYS-style code and is reported only for Siemens, where classic blocks do not initialise temporaries. Static variables of function blocks and programs are not checked: keeping a value from one cycle to the next is what they are for. Structures and arrays, bodies with JMP or __TRY, and Rockwell code (which has no temporaries) are not checked.

Noncompliant

FUNCTION_BLOCK FB_Door
VAR_INPUT
    bOpenCmd : BOOL;
END_VAR
VAR_OUTPUT
    bMotor : BOOL;
END_VAR
VAR_TEMP
    bWasOpen : BOOL;
END_VAR
IF bOpenCmd AND NOT bWasOpen THEN
    bMotor := TRUE;
END_IF
bWasOpen := bOpenCmd;
END_FUNCTION_BLOCK

Compliant

FUNCTION_BLOCK FB_Door
VAR_INPUT
    bOpenCmd : BOOL;
END_VAR
VAR_OUTPUT
    bMotor : BOOL;
END_VAR
VAR
    bWasOpen : BOOL;
END_VAR
IF bOpenCmd AND NOT bWasOpen THEN
    bMotor := TRUE;
END_IF
bWasOpen := bOpenCmd;
END_FUNCTION_BLOCK
PLCA-Q011 Implicit narrowing conversion

Description

A value is converted implicitly to a type that cannot hold every value of its own type: a wider integer or bit string to a narrower one (DINT to INT, DWORD to WORD), a real to an integer, or LREAL to REAL — in an assignment, an input argument or an output argument. Also an integer constant that does not fit the target type.

Rationale

Implicit narrowing silently truncates: a counter stored in an INT wraps at 32767, a REAL assigned to an INT loses its fraction (and overflows above 32767), an LREAL position loses precision. Making the conversion explicit with a conversion function shows the reader that the range was considered, and is where a LIMIT belongs. PLCopen Coding Guidelines rule CP25 Data types conversion should be explicit.

Untyped literals take the type of the other operand (nInt + 1 stays INT, MAX(0.0, rSpeed) stays REAL), so they never cause a finding by themselves; named constants count by value, and one that fits is fine. Conversions between signed and unsigned types of the same size, and from integers to reals, are not reported. Rockwell code is not checked: Logix converts on assignment by design and has no conversion functions to make it explicit.

Noncompliant

FUNCTION_BLOCK FB_Count
VAR_INPUT
    diPulses : DINT;
    rSpeed : REAL;
END_VAR
VAR
    nPulses : INT;
    nSpeed : INT;
END_VAR
nPulses := diPulses;
nSpeed := rSpeed;
END_FUNCTION_BLOCK

Compliant

FUNCTION_BLOCK FB_Count
VAR_INPUT
    diPulses : DINT;
    rSpeed : REAL;
END_VAR
VAR
    nPulses : INT;
    nSpeed : INT;
END_VAR
nPulses := DINT_TO_INT(LIMIT(-32768, diPulses, 32767));
nSpeed := REAL_TO_INT(rSpeed);
END_FUNCTION_BLOCK
PLCA-P005 Pointer dereference without a check

Description

A pointer is dereferenced (p^) in a body that never compares it with 0, tests it with __ISVALIDREF or assigns it from ADR(…) before the dereference.

Rationale

Dereferencing a null pointer raises an access violation and stops the PLC (CODESYS, TwinCAT); a stale or zero pointer passed in by a caller is a classic cause of a controller crash after an online change. Check the pointer before using it, or use a REFERENCE with __ISVALIDREF. The check is approximate: any comparison of the pointer with 0 earlier in the body, or in a condition around the dereference, counts. A pointer member of a function block that the block's own code assigns (in FB_init or a setter method) is treated as part of the object's contract and not reported. One finding per pointer and body.

Noncompliant

FUNCTION F_Read : INT
VAR_INPUT
    pValue : POINTER TO INT;
END_VAR
F_Read := pValue^;
END_FUNCTION

Compliant

FUNCTION F_Read : INT
VAR_INPUT
    pValue : POINTER TO INT;
END_VAR
IF pValue <> 0 THEN
    F_Read := pValue^;
END_IF
END_FUNCTION
PLCA-S002 Externally writable value used without a check

Description

A value that can be written from outside the PLC — by an HMI, a SCADA system or another network client — drives a physical output, or is used as an array index, with no range or validity check in between.

Rationale

Anything an operator panel or network client can write must be treated as untrusted: a typing error, a misconfigured HMI or an attacker can send any value. A setpoint passed straight to an analog output can drive the process outside its limits; a command bit wired straight to an output bypasses every interlock; an index that is out of range faults the controller (Rockwell major fault, CODESYS exception) or overwrites neighbouring data. Top 20 Secure PLC Coding Practices (ISA GCA / admeritia, 2021), practice 8 "Validate HMI input variables at the PLC, not just at the HMI" and practice 9 "Validate indirections".

Externally writable means: Rockwell controller and program tags with ExternalAccess="Read/Write" (the default) that no logic of the project writes; Siemens data block members that are not ExternalWritable := 'False' and that no block writes; in CODESYS, TwinCAT and PLCopen, where any symbol may be reachable, variables with an OPC UA attribute or whose name or list name matches externalPattern (HMI, SCADA, VISU, OPC as a word of the name). Function block and Add-On Instruction instances are never sources: their members are written by the block's own logic.

A use counts as checked when the value is compared, limited (LIMIT, MIN, MAX, SEL, MUX, ladder LIM), used as a CASE selector or overwritten earlier in the body or in a condition around the use. Only pass-through is reported: an output assigned from the value and constants alone, or set under a condition on the value alone. An interlock in the expression is a check and silences the finding.

Noncompliant

VAR_GLOBAL
    GVL_HMI_rSpeedSetpoint : REAL;
    GVL_HMI_nRecipe : INT;
END_VAR

PROGRAM P_Drive
VAR
    qrSpeedOut AT %QD4 : REAL;
    arRecipes : ARRAY[0..9] OF REAL;
    rRecipe : REAL;
END_VAR
qrSpeedOut := GVL_HMI_rSpeedSetpoint;
rRecipe := arRecipes[GVL_HMI_nRecipe];
END_PROGRAM

Compliant

VAR_GLOBAL
    GVL_HMI_rSpeedSetpoint : REAL;
    GVL_HMI_nRecipe : INT;
END_VAR

PROGRAM P_Drive
VAR
    qrSpeedOut AT %QD4 : REAL;
    arRecipes : ARRAY[0..9] OF REAL;
    rRecipe : REAL;
END_VAR
qrSpeedOut := LIMIT(0.0, GVL_HMI_rSpeedSetpoint, 1500.0);
IF GVL_HMI_nRecipe >= 0 AND GVL_HMI_nRecipe <= 9 THEN
    rRecipe := arRecipes[GVL_HMI_nRecipe];
END_IF
END_PROGRAM
PLCA-S003 Suspicious hidden trigger

Description

Logic that waits for a moment or a value nobody sets by accident: a date compared to be on or after an absolute date, a real-time clock value compared to be on or after a calendar year, an equality comparison with a "magic" constant (hexspeak such as 16#DEADBEEF, 16#C0FFEE, or leet numbers such as 1337), or a timer that runs from start-up and fires only after a long delay.

Rationale

This is the shape of a logic bomb or a backdoor: code that behaves normally during commissioning and tests, and does something else on a given date, after weeks of operation, or when a value only an insider knows is written. Such code has been found in sabotage and research cases, and a code review is the best place to catch it. Each finding asks a reviewer to confirm what the condition enables. Not reported, because they are normal: daily schedules (time-of-day comparisons), "before" comparisons (a clock that is not set yet), dates up to the year 2000 (the 1970 epoch and S7's DT#1990-01-01 mean "not set") and from 2100 (range bounds, the end of DT in 2106), comparisons inside test assertions, short start-up delays, timers the POU also resets (tmr(IN := FALSE), a periodic cycle) and the 32-bit TIME maxima (T#49D17H2M47S295MS, T#24D20H31M23S647MS, T#24D), the usual "no timeout" values.

Clock sources recognised: the IEC RTC block, CODESYS SysTimeRtcGet, TwinCAT NT_GetTime, FB_LocalSystemTime, F_GetSystemTime, Siemens RD_LOC_T/RD_SYS_T, and Rockwell GSV(WallClockTime, …).

Noncompliant

PROGRAM P_Pump
VAR
    fbClock : RTC;
    bRun : BOOL;
    nCode : DINT;
END_VAR
fbClock(EN := TRUE);
IF fbClock.CDT >= DT#2027-01-01-00:00:00 THEN
    bRun := FALSE;
END_IF
IF nCode = 16#DEADBEEF THEN
    bRun := TRUE;
END_IF
END_PROGRAM

Compliant

PROGRAM P_Pump
VAR
    fbClock : RTC;
    bRun : BOOL;
    bNight : BOOL;
END_VAR
fbClock(EN := TRUE);
bNight := DT_TO_TOD(fbClock.CDT) >= TOD#22:00:00;
bRun := NOT bNight;
END_PROGRAM

PLCA-Q015 Naming convention

Description

A variable whose name does not start with the prefix for its type (bStart for a BOOL, fbTimer for an instance), or a function block, function, interface or user type whose name does not start with its kind's prefix (FB_, F_, I_, ST_, E_). Off by default; select PLCA-Q015 to run it, and set the prefixes to your team's convention.

Rationale

Type prefixes let a reader see what a name holds without looking up its declaration, and a consistent style makes code from different engineers read alike. PLCopen Coding Guidelines rules N2 Define type prefixes for variables and N10 Define prefixes for user defined types. The defaults follow the widespread CODESYS/Beckhoff style; every prefix is a regular expression parameter. A scope prefix (scopePrefix, e.g. g_ for globals) may come first, and the type prefix must be followed by an upper-case letter, a digit or _.

PLCA-L001 Contradictory nested condition

Description

An IF, ELSIF, WHILE condition or CASE label that can never be true where it stands, given the enclosing conditions (and nothing changed their operands in between): its branch never runs.

Rationale

The inner test contradicts what the outer test already established: IF nLevel > 100 THEN IF nLevel < 50 THEN. Either the inner condition is wrong (a typo in the limit, the wrong variable) or the code is dead. Both need a look.

The analysis follows assignments, calls and loops: a write to an operand between the two tests, a call that may change it (a global, a VAR_IN_OUT, an FB output), a pointer or reference to it, or a jump label in between drops what was known. Conditions fixed by constants (IF cSimulation THEN) are configuration switches and are not folded.

When the proof relies on a global that a task other than this POU's writes (see PLCA-P004), the finding is reported at info: the other task may change the value between the two tests, so the branch may run after all � itself a sign of a race.

Noncompliant

PROGRAM P_Test
VAR
    nLevel : INT;
    bPump : BOOL;
    bAlarm : BOOL;
END_VAR
IF nLevel > 100 THEN
    IF nLevel < 50 THEN
        bAlarm := TRUE;
    END_IF
END_IF
END_PROGRAM

Compliant

PROGRAM P_Test
VAR
    nLevel : INT;
    bPump : BOOL;
    bAlarm : BOOL;
END_VAR
IF nLevel > 100 THEN
    nLevel := 0;
    IF nLevel < 50 THEN
        bAlarm := TRUE;
    END_IF
END_IF
END_PROGRAM
